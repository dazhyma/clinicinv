# Clinic Inventory System

Внутренняя веб-система учёта инвентаря и расходных материалов клиники.

Источник истины по требованиям — [`Clinic_Inventory_System_TZ_RU.md`](./Clinic_Inventory_System_TZ_RU.md).
Аналитика — в [`docs/`](./docs): требования, модель данных, статусные модели,
критерии приёмки, открытые вопросы, принятые технические решения.

**Статус: Спринт 1 (фундамент).** Готовы схема БД, доменный слой, авторизация и
тесты. Экраны инвентаря, экран сканирования, печать этикеток и загрузка фото —
следующие спринты.

## Стек

| Слой | Технология |
| --- | --- |
| Приложение | Next.js 15 (App Router), React 19, TypeScript strict |
| БД | SQLite (`better-sqlite3`) в режиме WAL, Drizzle ORM |
| Стили | Tailwind CSS 4 |
| Сессии | своя реализация: таблица сессий + httpOnly cookie |
| Пароли | argon2id (`@node-rs/argon2`) |

| Фото | `sharp` (используется со спринта загрузки фото) |
| Тесты | Vitest |

Docker и PostgreSQL не требуются.

## Требования к среде

Node.js >= 20.11 (проверено на 24.16), npm (проверено на 11.13).

## Запуск

```bash
npm install

cp .env.example .env
# отредактировать .env: задать SEED_ADMIN_PASSWORD и SEED_STAFF_PASSWORD

npm run db:migrate   # применить миграции, создать файл БД
npm run db:seed      # создать два аккаунта из переменных окружения

npm run dev          # http://localhost:3000
```

Файл `.env` в репозиторий не попадает (§15). В репозитории лежит только
`.env.example`. Пароли аккаунтов существуют исключительно в виде argon2id-хеша.

## Инварианты, которые держит код

Это система учёта денег и остатков. Перечисленное ниже — раздел 18 ТЗ; любой
код, который это ломает, неверен, даже если проходит тесты.

**Остатки.** Всякое изменение остатка — отдельная запись `inventory_movements`
с типом и `idempotency_key`. Прямая запись в `items.current_quantity` мимо
журнала отсутствует в коде и отвергается в `updateItem()`. Инвариант
`current_quantity == SUM(quantity_delta)` проверяется функцией
`findStockInvariantMismatches()` и покрыт тестами.

**Идемпотентность.** Ключ приходит от клиента и проверяется уникальным индексом
БД, а не памятью приложения. Повторная отправка возвращает результат первой
операции как успех, а не ошибку. Ключ Void детерминирован
(`void:{operationId}:item:{itemId}`) — это машинная гарантия того, что второй
Void не вернёт остатки повторно.

**Транзакции.** Все изменения остатка — в `BEGIN IMMEDIATE`. Скан пака
добавляет либо все позиции, либо ни одной.

**Стоимость.** При добавлении предмета в операцию копируются снимки названия,
внутреннего кода, SKU, reference number и стоимости за единицу;
`line_total = quantity × unit_cost_snapshot`. Изменение текущей цены, состава
пака или названия не пересчитывает ни завершённые операции, ни уже добавленные
строки активной.

**Операции.** Каждое действие сохраняется на сервере немедленно. Автозавершения
по таймеру в коде нет: статус меняют только `finishOperation()` и
`voidOperation()` по явному действию пользователя. Logout, истечение сессии и
перезапуск сервера не меняют статус и не возвращают предметы на склад.
Несколько активных операций сосуществуют.

**Доступ.** Роль проверяется на сервере на каждом запросе и повторно внутри
доменных сервисов. Admin-действие из-под Staff отклоняется, даже если вызвано
напрямую в обход UI.

**Приватность.** В схеме нет полей с именем пациента, датой рождения, телефоном,
номером карты, Symplast Patient Code; нет таблицы сопоставления операции с
пациентом. Код операции — случайный. Проверяется тестом, сканирующим все
столбцы всех таблиц.

## Эксплуатация

### Резервное копирование и восстановление

**Создание копии.**

```bash
npm run db:backup                          # ./data/backups/clinic-<YYYYMMDD-HHMMSS>.db
npm run db:backup -- /Volumes/usb/clinic.db  # копия в заданный файл
```

Скрипт (`scripts/backup.ts`) использует штатный механизм SQLite `VACUUM INTO`
и затем проверяет копию `PRAGMA integrity_check` и пересчётом предметов,
операций и движений. Простое `cp data/clinic.db …` **небезопасно**: база
работает в режиме WAL, часть подтверждённых транзакций в момент копирования
находится в файле `-wal`, и такая копия оказывается неполной или битой.
Существующий файл `VACUUM INTO` не перезаписывает — вчерашняя копия не может
быть затёрта сегодняшней.

Копия — обычный файл SQLite: одна база, без сопутствующих `-wal`/`-shm`.
Загруженные фотографии (`data/uploads/`) в неё **не входят** и копируются
отдельно любым файловым способом — они неизменяемы после записи.

**Восстановление.**

1. Остановить приложение (`npm run start` / systemd-юнит). Пока сервер пишет в
   базу, подменять файл нельзя.
2. Сохранить текущее состояние на всякий случай:
   `mv data/clinic.db data/clinic.broken.db` (вместе с `-wal` и `-shm`, если они
   есть).
3. Скопировать резервную копию на место рабочего файла:
   `cp data/backups/clinic-20260727-020000.db data/clinic.db`.
4. Проверить: `npm run db:migrate` — команда применит миграции, которых в копии
   ещё нет, и напечатает журнал; для актуальной копии выведет
   `Applied: nothing new`.
5. Запустить приложение и убедиться, что открываются разделы Inventory и
   Operations и активные операции на месте.

Восстановление возвращает систему к моменту снятия копии: операции, движения и
корректировки, выполненные позже, теряются. Это ещё один довод в пользу частых
копий — периодичность выбирает клиника.

**Расписание не настроено** (Q-42, §22): периодичность, глубина хранения и место
хранения копий — решение по инфраструктуре и заказчиком не утверждено. Скрипт
рассчитан на вызов извне (cron / launchd / systemd timer) и на ручной запуск
перед обновлением системы. Копии на том же диске, что и рабочая база, защищают
от ошибки оператора, но не от отказа диска.

**HTTPS (§15, NFR-11).** Обеспечивается развёртыванием (обратный прокси).
В продакшене обязательно `COOKIE_SECURE=true`.
