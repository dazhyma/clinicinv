# Техническое задание

## Веб-система учёта инвентаря и расходных материалов клиники

**Версия:** 1.0  
**Статус:** первоначальное техническое задание для разработки MVP  
**Основная цель:** создать максимально простую и быструю веб-систему для учёта складских остатков и расходных материалов, использованных во время операций.

---

## 1. Назначение системы

Система должна заменить неудобный процесс оперативного учёта расходных материалов в Symplast.

Symplast остаётся официальной системой клиники, однако новая веб-система используется как отдельный рабочий инструмент для:

- ведения внутреннего инвентаря;
- присвоения предметам постоянных внутренних штрихкодов;
- быстрого сканирования расходных материалов во время операции;
- создания цифровых наборов часто используемых предметов;
- автоматического уменьшения складских остатков;
- фиксации фактической себестоимости каждой операции;
- последующего ручного переноса необходимых данных в Symplast.

Главный приоритет интерфейса — скорость и удобство. Во время операции сотрудники не должны тратить время на поиск предметов, переходы между страницами, повторные подтверждения или ожидание загрузки.

---

## 2. Основные принципы

1. Система имеет два основных раздела:
   - **Inventory / Инвентарь**
   - **Operations / Операции**

2. Для доступа к сайту обязательно требуется авторизация.

3. В системе предусмотрены только два общих аккаунта:
   - **Staff**
   - **Admin**

4. Система не хранит:
   - имя пациента;
   - дату рождения;
   - адрес;
   - номер телефона;
   - номер медицинской карты;
   - Symplast Patient Code;
   - название или описание конкретной медицинской процедуры, если оно может раскрывать лишние сведения;
   - любые другие данные, позволяющие установить личность пациента.

5. Каждой операции присваивается собственный случайный внутренний код. Он идентифицирует только запись об использовании материалов и никак не связан с пациентом или Symplast.

6. Активная операция не может исчезнуть, завершиться или обнулиться автоматически.

7. Каждое изменение во время операции должно сохраняться сразу.

8. Себестоимость завершённой операции является зафиксированным историческим значением и не изменяется при последующем редактировании стоимости предметов.

9. Все внутренние штрихкоды создаются системой автоматически и остаются постоянными.

---

# 3. Авторизация и уровни доступа

## 3.1. Страница входа

При открытии сайта неавторизованный пользователь должен видеть только страницу входа.

Страница содержит:

- поле username;
- поле password;
- кнопку **Log In**;
- сообщение об ошибке при неверных данных.

На странице не должно быть отдельного переключателя Staff/Admin. Уровень доступа определяется введёнными учётными данными.

Пароли не должны храниться в базе данных в открытом виде.

После нескольких подряд неудачных попыток входа система должна временно ограничивать дальнейшие попытки.

## 3.2. Аккаунт Staff

Аккаунт Staff предназначен для сотрудников, работающих с системой во время операций.

Staff может:

- начать новую операцию;
- возобновить активную операцию;
- сканировать отдельные предметы;
- сканировать паки;
- искать предмет вручную;
- изменять количество предмета в активной операции;
- отменить последнее сканирование;
- завершить операцию;
- просматривать доступное количество предметов в инвентаре;
- просматривать разрешённую историю операций.

Staff не может:

- создавать и удалять аккаунты;
- менять пароли через интерфейс без соответствующего разрешения;
- создавать, редактировать или удалять предметы;
- менять стоимость предметов;
- создавать или менять состав паков;
- вручную корректировать складские остатки;
- аннулировать или удалять операции;
- видеть административные настройки.

Отображение себестоимости и финансовых итогов для Staff должно настраиваться. По умолчанию во время операции Staff видит предметы и количества, но не обязан видеть стоимость.

## 3.3. Аккаунт Admin

Admin имеет полный доступ к системе.

Admin может:

- выполнять все действия Staff;
- создавать и редактировать предметы;
- загружать и заменять фотографии предметов;
- менять текущую себестоимость предметов;
- получать новые поставки;
- выполнять ручную корректировку остатков;
- создавать и редактировать паки;
- просматривать себестоимость операций;
- просматривать завершённые и аннулированные операции;
- аннулировать операции;
- управлять основными настройками;
- менять пароли двух аккаунтов.

## 3.4. Выход и окончание сессии

Выход из аккаунта, закрытие браузера или истечение сессии не должны:

- завершать активную операцию;
- удалять активную операцию;
- удалять отсканированные предметы;
- возвращать предметы на склад;
- менять статус операции.

После повторного входа система должна предложить возобновить активную операцию.

После входа пользователь видит две крупные и очевидные кнопки:

## Inventory

Подпись: **Manage items, stock, packs, and barcodes**

## Operations

Подпись: **Start scanning or review operations**

Для Admin также может отображаться небольшая кнопка **Settings**, но она не должна отвлекать от двух основных рабочих разделов.

Интерфейс должен быть адаптирован для:

- компьютера;
- планшета;
- мобильного устройства;
- сенсорного экрана.

# 5. Раздел Inventory

## 5.1. Структура раздела

Раздел Inventory содержит как минимум две вкладки:

1. **Items**
2. **Packs**

Дополнительные действия:

- **Add New Item**
- **Receive Stock**
- **Inventory Count**
- поиск;
- фильтры;
- отображение предметов с низким остатком.

## 5.2. Карточка предмета в списке

Каждый предмет отображается отдельной компактной строкой или карточкой.

Карточка должна содержать:

- фотографию предмета;
- название предмета;
- текущее количество;
- себестоимость за одну единицу;
- кнопку **Edit**;
- кнопку **View Barcode**.

Пример:

> [Фото] Gauze 4×4  
> In stock: 147 · Cost: $3.25  
> [Edit] [View Barcode]

На небольшом экране элементы могут переноситься на следующую строку, но кнопки должны оставаться крупными и удобными.

## 5.3. Поиск и фильтрация

Поиск должен работать как минимум по:

- названию;
- внутреннему коду;
- reference/catalog number.

При необходимости должны поддерживаться фильтры по:

- категории;
- месту хранения;
- наличию;
- низкому остатку.

## 5.4. Создание нового предмета

Форма **Add New Item** содержит:

- **Item Name** — обязательное поле;
- **Photo** — необязательное поле;
- **Reference / Catalog Number** — необязательное поле;
- **Cost per Unit** — обязательное поле;
- **Unit of Measurement** — обязательное поле;
- **Initial Quantity** — обязательное поле, может быть 0;
- **Category** — необязательное или настраиваемое поле;
- **Storage Location** — необязательное поле;
- **Low Stock Threshold** — необязательное поле;
- **Notes** — необязательное поле.

Возможные единицы измерения:

- each;
- box;
- pack;
- pair;
- mL;
- bottle;
- roll;
- другие настраиваемые варианты.

## 5.5. Автоматическая генерация внутреннего штрихкода

При сохранении нового предмета система автоматически:

1. создаёт уникальный внутренний идентификатор, например `ITM-000127`;
2. проверяет, что такой идентификатор ещё не существует;
3. связывает идентификатор с созданным предметом;
4. генерирует из него сканируемый штрихкод;
5. сохраняет идентификатор как постоянный.

Штрихкод:

- не зависит от штрихкода производителя;
- не должен меняться при изменении названия, стоимости, reference number, фотографии или количества;
- не может повторно использоваться для другого предмета;
- должен корректно считываться используемыми в клинике сканерами;
- должен иметь читаемую человеком текстовую строку под графическим кодом.

Предпочтительный формат для внутренних кодов — штрихкод типа Code 128 либо другой формат, совместимый с фактически используемым сканером.

Графическое изображение штрихкода может генерироваться динамически в SVG. Система не обязана хранить отдельный PNG для каждого предмета.

## 5.6. Просмотр и печать штрихкода

Кнопка **View Barcode** открывает отдельную чистую страницу или новую вкладку.

Страница содержит:

- название предмета;
- reference/catalog number, если он задан;
- графический штрихкод;
- текстовый внутренний код;
- выбор количества копий;
- кнопку **Print**;
- опциональную кнопку **Download PNG**;
- опциональную кнопку **Download SVG**.

Печатная страница не должна содержать:

- навигационное меню;
- лишние кнопки;
- фоновые элементы;
- карточку предмета;
- элементы, не предназначенные для этикетки.

Должна поддерживаться:

- печать одной этикетки;
- печать нескольких одинаковых этикеток;
- печать на обычном листе;
- настройка или выбор размера этикетки;
- качественная печать без размытия.

Если пользователь скачивает штрихкод в PNG, над штрихкодом необходимо оставить небольшое свободное пространство.

Индивидуальные SVG, PNG, Print и массовые PDF используют один системный код
`ITM-######`. Читаемый код под графикой обязан совпадать с закодированным.

## 5.7. Редактирование предмета

Кнопка **Edit** открывает полную карточку предмета.

Admin может изменить:

- название;
- фотографию;
- reference/catalog number;
- текущую стоимость;
- единицу измерения;
- категорию;
- место хранения;
- порог низкого остатка;
- заметки;
- активный/неактивный статус.

Внутренний код и штрихкод нельзя случайно изменить через стандартную форму.

Изменение текущей стоимости влияет только на:

- будущие сканирования;
- будущие операции;
- текущую отображаемую стоимость предмета;
- текущую расчётную стоимость цифровых паков.

Изменение стоимости не должно менять данные завершённых операций.

## 5.8. Добавление поставки

Функция **Receive Stock** позволяет:

1. отсканировать внутренний штрихкод или найти предмет вручную;
2. проверить карточку найденного предмета и нажать **Confirm Item**;
3. указать количество поступивших единиц;
4. при необходимости указать новую себестоимость единицы;
5. подтвердить поступление;
6. увеличить текущий остаток;
7. вернуться к сканированию следующего предмета.

Само распознавание штрихкода и подтверждение найденного предмета не меняют
остаток. Движение создаётся только после сохранения формы поставки.

Если себестоимость новой поставки отличается от предыдущей, система должна позволить Admin выбрать или применить предусмотренный метод учёта стоимости. Для MVP допустимо использовать новую указанную стоимость как текущую стоимость для будущих операций, не изменяя историю.

## 5.9. Ручная корректировка остатка

Admin может увеличить или уменьшить остаток вручную.

При корректировке указываются:

- предмет;
- величина изменения или новое фактическое количество;
- причина корректировки.

Примеры причин:

- damaged;
- expired;
- missing;
- inventory correction;
- received outside normal process;
- other.

Ручная корректировка не должна менять завершённые операции.

## 5.10. Инвентаризация

Режим **Inventory Count** должен позволять быстро сверять физические остатки.

Базовый процесс:

1. Admin начинает новую инвентаризацию;
2. сканирует предмет;
3. проверяет карточку и нажимает **Confirm Item**;
4. вводит физически найденное количество;
5. система показывает ожидаемое количество;
6. система показывает разницу;
7. после подтверждения система корректирует остаток;
8. камера возвращается к сканированию следующего предмета.

Распознавание и **Confirm Item** не корректируют остаток: до применения всей
инвентаризации введённые количества остаются черновиком.

Незавершённая инвентаризация должна сохраняться при обновлении страницы.

## 5.11. Низкий остаток

Для каждого предмета можно указать **Low Stock Threshold**.

Если текущее количество равно или ниже порога:

- предмет визуально выделяется;
- он появляется в фильтре или списке Low Stock.

Автоматический заказ поставщику в MVP не требуется.

# 6. Паки

## 6.1. Назначение

Пак — цифровой набор предметов, которые обычно используются вместе в одинаковом количестве.

Пример:

**Basic Pack**

| Предмет | Количество |
| --- | ---: |
| Gauze 4×4 | 2 |
| Gloves L | 3 |
| Syringe 10 mL | 1 |

Сканирование одного штрихкода пака добавляет в операцию все предметы из его состава.

## 6.2. Данные пака

Пак содержит:

- название;
- необязательную фотографию;
- автоматически созданный системный код;
- автоматически созданный уникальный штрихкод;
- список включённых предметов;
- количество каждого предмета;
- активный/неактивный статус;
- необязательные заметки.

## 6.3. Создание пака

Admin:

1. нажимает **Add New Pack**;
2. вводит название;
3. выбирает предметы;
4. указывает количество каждого предмета;
5. сохраняет пак.

При сохранении система автоматически создаёт уникальный код, например `PCK-000015`, и генерирует штрихкод.

## 6.4. Стоимость пака

Текущая стоимость пака рассчитывается автоматически:

> сумма `(текущая стоимость предмета × количество предмета в паке)`

Стоимость пака не вводится вручную как независимая сумма.

При изменении текущей стоимости предмета текущая расчётная стоимость пака обновляется.

Это обновление не должно менять стоимость паков, уже добавленных в завершённые операции.

## 6.5. Остатки паков

В MVP пак является цифровым сокращением для сканирования, а не отдельным физическим складским объектом.

Поэтому:

- пак не имеет самостоятельного складского количества;
- при сканировании уменьшаются остатки отдельных предметов внутри пака;
- один и тот же предмет может входить в несколько паков;
- предмет также можно сканировать отдельно.

Если в будущем клиника начнёт физически собирать и хранить готовые паки, отдельный режим учёта физических паков должен рассматриваться как дополнительная функция, а не смешиваться с текущей логикой.

## 6.6. Просмотр и печать штрихкода пака

Для пака доступна кнопка **View Barcode** с той же логикой печати, что и для отдельного предмета.

На этикетке отображаются:

- название пака;
- штрихкод;
- внутренний код пака.

## 6.7. Изменение состава пака

Изменение состава пака влияет только на будущие сканирования.

Если пак уже использовался:

- предыдущие операции сохраняют исходный состав;
- количество предметов в завершённых операциях не меняется;
- историческая стоимость не пересчитывается.

# 7. Раздел Operations

## 7.1. Основной принцип

Раздел Operations должен работать как максимально простой кассовый терминал:

> начать операцию → сканировать → при необходимости исправить → завершить.

Во время активной операции пользователь не должен переходить между несколькими страницами.

## 7.2. Список операций

Раздел содержит:

- кнопку **Start New Operation**;
- блок активных операций;
- историю завершённых операций;
- историю аннулированных операций для Admin;
- поиск и фильтры.

В списке операции могут отображаться:

- внутренний код операции;
- статус;
- дата и время создания;
- дата и время завершения;
- условная категория процедуры, если она используется;
- количество позиций;
- общая себестоимость для Admin.

## 7.3. Создание операции

При нажатии **Start New Operation** система:

1. создаёт уникальный случайный код операции;
2. создаёт запись со статусом **Active**;
3. при необходимости предлагает выбрать общую категорию процедуры;
4. открывает экран сканирования;
5. сразу сохраняет созданную операцию.

Код операции:

- не является кодом пациента;
- не совпадает с Symplast Patient Code;
- не создаётся на основе данных пациента;
- не должен иметь отдельной таблицы сопоставления с пациентом;
- используется только для различения записей в этой системе.

## 7.4. Экран активной операции

На экране отображаются:

- код операции;
- статус **Active**;
- категория, если она используется;
- индикатор готовности сканера;
- последний отсканированный предмет или пак;
- список добавленных предметов;
- количество каждого предмета;
- кнопки `−` и `+`;
- кнопка удаления строки;
- кнопка **Undo Last Scan**;
- кнопка **Manual Item Search**;
- индикатор сохранения/синхронизации;
- кнопка **Finish Operation**.

Общая стоимость может отображаться для Admin. Для Staff её отображение настраивается.

## 7.5. Работа сканера

Система поддерживает два способа сканирования:

- камеру iPhone/iPad и Android-устройства в Safari или Chrome;
- USB/Bluetooth-сканер в режиме эмуляции клавиатуры (HID).

Для HID поле сканирования должно быть готово постоянно. Камерный экран содержит
заметную рамку и подсказку **Place one barcode inside the frame**. По возможности
распознавание ограничивается центральной областью внутри рамки.

После сканирования система:

1. распознаёт внутренний код;
2. находит предмет или пак;
3. временно приостанавливает распознавание других кодов;
4. показывает поверх камеры карточку с фотографией, названием, системным
   кодом, reference number при наличии и текущим остатком предмета;
5. не изменяет операцию и складские остатки до явного подтверждения.

Карточка содержит кнопки **Add**, **Scan Again** и **Cancel**. Для пака
показываются отметка **Pack**, количество входящих позиций, краткий состав и
**View Contents**, если состав не помещается.

После **Add** система:

1. добавляет предмет или пак в операцию;
2. выполняет существующую логику списания и немедленно сохраняет изменение;
3. показывает крупное визуальное подтверждение;
4. воспроизводит звуковой сигнал, если это поддерживается устройством;
5. закрывает карточку, оставляет камеру открытой и возвращается к распознаванию.

**Scan Again** отклоняет найденный объект без изменения данных и возобновляет
камеру. **Cancel** ничего не добавляет, закрывает камеру и возвращает к экрану
операции. Если в кадре несколько штрихкодов, система выбирает один; пользователь
проверяет карточку и при ошибочном выборе нажимает **Scan Again**.

Сам факт распознавания, обновление страницы, закрытие карточки или повторное
открытие камеры не должны добавлять предмет и не должны уменьшать остаток.

Пример подтверждения:

> Gauze 4×4 added

или:

> Basic Pack added — 6 items

Успешное сканирование обозначается зелёным цветом. Ошибка или неизвестный штрихкод обозначаются красным цветом и сопровождаются понятным сообщением.

## 7.6. Повторное сканирование

Если тот же предмет сканируется повторно:

- система увеличивает его количество;
- система не обязана создавать отдельную строку;
- каждое сканирование должно сохраняться в истории действий активной операции.

## 7.7. Сканирование пака

При сканировании пака:

1. система находит сохранённый состав пака и показывает карточку подтверждения;
2. до **Add** не меняет никаких данных;
3. после **Add** добавляет все предметы в указанном количестве;
4. сохраняет текущую стоимость каждого предмета;
5. уменьшает складские остатки отдельных предметов;
6. показывает пользователю, что пак был успешно добавлен.

В интерфейсе должно быть видно, какие предметы были добавлены через пак.

При необходимости пользователь может изменить фактически использованное количество конкретного предмета после добавления пака.

## 7.8. Ручной поиск

Если штрихкод повреждён или сканер не работает, пользователь нажимает **Manual Item Search**.

Поиск работает по:

- названию;
- внутреннему коду;
- reference/catalog number.

После выбора предмет добавляется в активную операцию по той же логике, что и при сканировании.

## 7.9. Исправления во время операции

Пользователь может:

- отменить последнее сканирование;
- увеличить количество;
- уменьшить количество;
- удалить ошибочно добавленный предмет;
- добавить предмет вручную.

Каждое действие:

- немедленно сохраняется;
- корректирует складской остаток;
- корректирует расчётную стоимость активной операции.

Если количество уменьшается, соответствующее количество возвращается на склад.

## 7.10. Проверка доступного количества

Если пользователь пытается добавить больше предметов, чем числится на складе, система должна:

- показать предупреждение;
- не скрывать проблему;
- не завершать операцию автоматически.

Окончательное поведение настраивается:

- либо запретить добавление сверх остатка;
- либо позволить продолжить с явным предупреждением и создать отрицательный остаток.

Для MVP предпочтительно разрешить Admin выбрать общий режим. В условиях операции блокировка может быть опасно неудобной, поэтому рекомендуемый режим — разрешить сканирование с ярким предупреждением.

# 8. Сохранение и восстановление активной операции

## 8.1. Обязательное немедленное сохранение

Активная операция сохраняется:

- сразу после создания;
- после каждого сканирования;
- после добавления пака;
- после ручного добавления предмета;
- после изменения количества;
- после удаления предмета;
- после Undo;
- после изменения категории;
- после любого другого значимого действия.

Нельзя хранить всю операцию только в памяти страницы до нажатия Finish.

## 8.2. Обновление или закрытие страницы

Следующие события не должны менять статус операции и не должны приводить к потере данных:

- случайное обновление страницы;
- закрытие вкладки;
- закрытие браузера;
- переход на другую страницу сайта;
- выход из аккаунта;
- истечение сессии;
- перезапуск устройства;
- временная потеря интернета;
- перезапуск сайта или сервера.

## 8.3. Возобновление

При возвращении в раздел Operations система показывает:

> Active operation found  
> Case: K7P4Q  
> 14 items scanned  
> [Resume Operation]

После нажатия **Resume Operation**:

- восстанавливается полный список;
- восстанавливаются количества;
- восстанавливаются зафиксированные цены;
- восстанавливается текущий итог;
- сканер снова готов к работе.

## 8.4. Работа при временной потере интернета

Если интернет временно пропал:

- новые действия должны по возможности сохраняться локально на устройстве;
- пользователь должен видеть статус **Offline**;
- должно отображаться количество действий, ожидающих синхронизации;
- после восстановления связи данные отправляются на сервер;
- один и тот же scan event не должен применяться дважды.

Пример:

> Offline — 3 changes waiting to sync

Если полноценный offline mode не войдёт в первую техническую версию, система как минимум не должна терять уже подтверждённые сервером данные и должна ясно предупреждать, что новые сканирования не синхронизированы.

## 8.5. Несколько активных операций

Система должна поддерживать сохранение более одной активной операции, поскольку незавершённая операция не должна блокировать клинику навсегда.

При попытке начать новую операцию при наличии активной система показывает:

- список активных операций;
- кнопку **Resume** рядом с каждой;
- кнопку **Start Another Operation**, если это разрешено.

Новая операция не должна перезаписывать существующую.

# 9. Статусы операции

## 9.1. Active

Операция создана и ещё не завершена.

Она остаётся Active неограниченно долго, пока пользователь явно не выполнит разрешённое действие.

Автоматическое завершение по времени запрещено.

## 9.2. Finished

Операция получает статус Finished только после:

1. нажатия **Finish Operation**;
2. показа подтверждения;
3. явного нажатия **Finish and Lock**.

Текст подтверждения:

> Finish this operation?  
> Quantities and costs will be locked.  
> [Cancel] [Finish and Lock]

После завершения:

- финансовые данные фиксируются;
- список предметов фиксируется;
- количества фиксируются;
- операция появляется в истории;
- она перестаёт отображаться как активная.

## 9.3. Voided

Admin может аннулировать активную или завершённую операцию.

Предпочтительное название действия — **Void Operation**, а не физическое удаление.

При аннулировании:

- операция исключается из обычных финансовых итогов;
- все списанные ею количества возвращаются в инвентарь;
- операция сохраняется в истории как Voided;
- повторное аннулирование невозможно;
- возврат остатков нельзя применить дважды.

Перед аннулированием система показывает:

> Void Operation K7P4Q?  
> All inventory deducted by this operation will be returned.  
> The operation will be excluded from financial totals.  
> [Cancel] [Void Operation]

Admin может указать причину аннулирования.

Физическое безвозвратное удаление записей из базы данных через обычный интерфейс не требуется.

# 10. Логика складских остатков

## 10.1. Добавление предмета в операцию

При добавлении предмета:

- количество на складе уменьшается на использованное количество;
- операция получает копию данных предмета и его стоимости;
- изменение сохраняется.

## 10.2. Удаление предмета из активной операции

При уменьшении количества или удалении предмета:

- соответствующее количество возвращается на склад;
- стоимость активной операции уменьшается;
- изменение сохраняется.

## 10.3. Аннулирование операции

При Void система возвращает ровно те количества, которые были списаны этой операцией.

Система не должна восстанавливать старое общее число остатков.

Пример:

1. На складе было 10 gauze.
2. Операция использовала 2, осталось 8.
3. Позже поступило ещё 20, стало 28.
4. Операция аннулирована.
5. Система возвращает 2, итоговый остаток становится 30.

## 10.4. Транзакционный принцип

Все изменения остатков должны храниться как отдельные движения:

- received;
- used in operation;
- returned from operation;
- manual adjustment;
- inventory count correction;
- void reversal.

Это предотвращает неправильный пересчёт при изменениях, совершённых после операции.

Каждое движение должно иметь уникальный идентификатор, чтобы повторная отправка запроса не списала или не вернула предмет дважды.

# 11. Фиксация себестоимости

## 11.1. Текущая стоимость предмета

В карточке предмета хранится его текущая себестоимость за единицу.

Стоимость означает **cost**, а не продажную цену.

## 11.2. Снимок стоимости

Когда предмет добавляется в операцию, система копирует в строку операции:

- название предмета на тот момент;
- внутренний код;
- reference number на тот момент;
- количество;
- стоимость одной единицы на тот момент;
- сумму строки.

Формула:

> line total = quantity × unit cost snapshot

## 11.3. Неизменяемость истории

Если после завершения операции Admin меняет:

- название предмета;
- reference number;
- текущую стоимость;
- состав пака;
- количество предметов в паке;

завершённая операция не должна пересчитываться.

Пример:

1. Во время операции Gauze 4×4 стоил $3.00.
2. Было использовано 2 единицы.
3. В операции сохранён итог $6.00.
4. Позже текущая стоимость изменена на $4.25.
5. Завершённая операция всё равно показывает $6.00.

Новая стоимость применяется только к будущим добавлениям.

## 11.4. Активная операция

Стоимость рекомендуется фиксировать в момент добавления предмета даже до завершения операции.

Если Admin меняет текущую стоимость, уже добавленные строки активной операции не должны самопроизвольно изменяться.

При удалении предмета и повторном добавлении применяется стоимость, действующая на момент нового добавления.

## 11.5. Общая себестоимость

Общая себестоимость операции:

> сумма всех line totals

Для Admin отображаются:

- отдельные строки;
- стоимость единицы;
- количество;
- сумма строки;
- общая стоимость.

Эти данные используются для последующего анализа прибыльности процедуры.

Доход и окончательная прибыль могут рассчитываться в отдельном модуле в будущем. В MVP обязательна точная себестоимость использованных материалов.

# 12. История и просмотр операции

## 12.1. История

История содержит:

- код операции;
- статус;
- дату создания;
- дату завершения или аннулирования;
- категорию, если используется;
- количество уникальных предметов;
- общее количество использованных единиц;
- общую себестоимость для Admin.

## 12.2. Карточка завершённой операции

Карточка показывает:

- код операции;
- статус;
- временные отметки;
- список предметов;
- источник добавления: отдельный scan или pack;
- количество;
- сохранённую стоимость единицы;
- сумму строки;
- общий итог.

## 12.3. Сводка для Symplast

Завершённая операция должна иметь удобную сводку для ручного переноса информации в Symplast.

Сводка содержит только необходимые рабочие данные:

- item name;
- reference number;
- quantity used;
- при необходимости cost;
- общий итог.

Сводка не содержит данных пациента.

Опционально:

- кнопка **Print Summary**;
- кнопка **Copy Summary**;
- экспорт в CSV или PDF на более позднем этапе.

# 13. Фотографии предметов

Admin может загрузить фотографию при создании или редактировании предмета.

Требования:

- поддержка распространённых форматов JPG, PNG и WebP;
- автоматическое уменьшение слишком больших изображений;
- одинаковое аккуратное отображение в карточках;
- placeholder, если фотография отсутствует;
- фотография не должна замедлять сканирование и работу операционного экрана.

Фотографии предметов не должны содержать данные пациентов.

# 14. Интерфейс и удобство использования

## 14.1. Общие требования

Интерфейс должен быть:

- простым;
- быстрым;
- визуально чистым;
- удобным для сенсорного экрана;
- понятным без длительного обучения;
- адаптивным;
- устойчивым к случайным нажатиям.

## 14.2. Требования к операционному экрану

На операционном экране:

- крупные кнопки;
- крупный текст;
- минимум лишних элементов;
- высокая контрастность;
- заметный последний отсканированный предмет;
- понятные зелёные и красные статусы;
- никакого подтверждения после каждого успешного сканирования;
- Undo всегда виден;
- Finish визуально отделён от обычных действий;
- Finish требует одного подтверждения.

## 14.3. Скорость

Обычное успешное сканирование должно визуально регистрироваться практически мгновенно.

Целевое время реакции интерфейса после считывания штрихкода — не более 500 мс при нормальном соединении.

Медленные операции записи не должны заставлять пользователя вручную перезагружать страницу.

## 14.4. Ошибки

Сообщения должны быть конкретными.

Хорошие примеры:

- **Barcode not found**
- **Item is inactive**
- **Only 2 units remain in inventory**
- **Changes are not synced — check connection**
- **Operation was already voided**

Плохие примеры:

- **Something went wrong**
- **Error 500**
- исчезновение действия без объяснения.

# 15. Безопасность

Сайт не должен быть доступен без авторизации.

Минимальные требования:

- HTTPS;
- безопасное хранение паролей;
- защищённые cookies/session tokens;
- разграничение Staff/Admin на серверной стороне;
- невозможность получить административный доступ простым изменением интерфейса в браузере;
- ограничение попыток входа;
- резервное копирование базы данных;
- защита загруженных файлов;
- отсутствие публичных URL, через которые можно просмотреть инвентарь или операции без входа;
- секреты и пароли не хранятся в публичном коде;
- журнал критических системных действий.

Хотя система проектируется без идентифицирующих данных пациента, необходимо сохранять принцип минимизации данных и не добавлять пациентские сведения в свободные заметки.

# 16. Надёжность и целостность данных

Система не должна:

- списывать один scan event дважды;
- возвращать остатки дважды;
- менять завершённую операцию после обновления стоимости;
- присваивать одинаковый штрихкод двум объектам;
- удалять активную операцию при перезагрузке;
- завершать операцию по таймеру;
- перезаписывать одну активную операцию другой;
- терять подтверждённые изменения;
- позволять Staff выполнять Admin-действия.

Для операций со складскими остатками необходимо использовать атомарные транзакции базы данных.

Если часть действия не может быть выполнена, система не должна оставлять данные в наполовину изменённом состоянии.

Пример: при сканировании пака либо корректно добавляются все его позиции, либо пользователь получает понятную ошибку. Нельзя списать половину пака и молча потерять остальное.

# 18. Критические бизнес-правила

Эти правила являются обязательными и не должны изменяться без отдельного решения:

1. В системе только два общих аккаунта: Staff и Admin.
2. Без авторизации сайт недоступен.
3. Система не хранит patient name или Symplast Patient Code.
4. Код операции является случайным кодом записи, а не идентификатором пациента.
5. Новый предмет автоматически получает уникальный постоянный штрихкод.
6. Новый пак автоматически получает уникальный постоянный штрихкод.
7. Изменение данных предмета не меняет его штрихкод.
8. View Barcode открывает отдельную удобную страницу печати.
9. Сканирование пака добавляет все его предметы и уменьшает их индивидуальные остатки.
10. Пак в MVP не имеет отдельного физического остатка.
11. Активная операция сохраняется после каждого действия.
12. Обновление страницы не завершает и не стирает операцию.
13. Активная операция остаётся активной неограниченно долго.
14. Операция завершается только после явного нажатия Finish and Lock.
15. Стоимость предмета копируется в операцию как snapshot.
16. Завершённая операция не пересчитывается после изменения стоимости.
17. Изменение состава пака не меняет старые операции.
18. При уменьшении количества в активной операции остаток возвращается.
19. При Void все списанные операцией количества возвращаются.
20. Void не возвращает старое общее количество, а создаёт обратные движения по конкретной операции.
21. Одну операцию нельзя аннулировать дважды.
22. Staff не может редактировать стоимость, предметы, паки или аннулировать операции.
23. При потере соединения пользователь получает явное предупреждение.
24. Одна активная операция не может быть молча перезаписана другой.

# 21. Критерии приёмки

Система считается готовой к первоначальному использованию, если успешно выполняются следующие проверки.

## 21.1. Штрихкоды

- новый предмет автоматически получает уникальный код;
- код превращается в сканируемый штрихкод;
- View Barcode открывается отдельно;
- штрихкод печатается чётко;
- изменение названия и стоимости не меняет код;
- два предмета не могут получить одинаковый код.

## 21.2. Активная операция

- пользователь создаёт операцию;
- сканирует несколько предметов;
- обновляет страницу;
- все предметы и количества остаются;
- закрывает браузер;
- повторно входит;
- операция доступна через Resume;
- операция не завершилась сама.

## 21.3. Пак

- Admin создаёт пак из нескольких предметов;
- система создаёт штрихкод пака;
- один scan добавляет весь состав;
- остатки каждого предмета уменьшаются на правильное количество;
- изменение состава пака позже не меняет завершённую операцию.

## 21.4. Стоимость

- предмет добавляется при стоимости $3.00;
- операция завершается;
- стоимость предмета меняется на $4.25;
- завершённая операция продолжает показывать $3.00 за единицу;
- новая операция использует $4.25.

## 21.5. Void

- операция списывает 2 единицы;
- после неё принимается новая поставка;
- Admin аннулирует операцию;
- система возвращает ровно 2 единицы;
- поставка остаётся учтённой;
- финансовая сумма аннулированной операции исключается;
- повторный Void невозможен.

## 21.6. Доступ

- неавторизованный пользователь не видит данные;
- Staff не может открыть Admin-функции;
- Admin может редактировать предметы и паки;
- logout не стирает активную операцию.

# 23. Итоговый пользовательский сценарий

## Подготовка инвентаря

1. Admin входит в систему.
2. Создаёт предмет.
3. Загружает фотографию и вводит данные.
4. Сайт автоматически создаёт внутренний штрихкод.
5. Admin нажимает View Barcode.
6. Открывается чистая печатная страница.
7. Admin печатает нужное количество этикеток.

## Создание пака

1. Admin создаёт Basic Pack.
2. Добавляет Gauze 4×4 ×2, Gloves L ×3 и другие предметы.
3. Сайт автоматически создаёт штрихкод пака.
4. Admin печатает этикетку.

## Использование во время операции

1. Staff входит в систему.
2. Нажимает Operations.
3. Нажимает Start New Operation.
4. Система создаёт случайный код.
5. Staff сканирует Basic Pack.
6. Все предметы пака добавляются автоматически.
7. Дополнительные предметы сканируются отдельно.
8. При ошибке Staff нажимает Undo или меняет количество.
9. Каждое действие сохраняется немедленно.
10. Даже после refresh операция остаётся активной.
11. После окончания Staff нажимает Finish Operation.
12. Подтверждает Finish and Lock.
13. Система фиксирует количества и стоимость.
14. Сводка используется для ручного переноса необходимых данных в Symplast.

## Аннулирование

1. Admin открывает операцию.
2. Нажимает Void Operation.
3. Подтверждает возврат остатков.
4. Система создаёт обратные движения по каждому предмету.
5. Операция получает статус Voided и исключается из финансовых итогов.
