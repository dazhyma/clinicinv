# Модель данных

Основа — раздел 17 ТЗ. Типы указаны логически (СУБД не выбрана): `id`, `text`, `int`, `decimal(p,s)`, `bool`, `enum`, `timestamp`, `json`. Конкретное отображение на типы СУБД — решение разработчика.

## Обозначения

| Обозначение | Значение |
| --- | --- |
| **PK** | первичный ключ |
| **FK** | внешний ключ |
| **NOT NULL** | обязательное поле |
| **U** | уникальное ограничение |
| **U-DB** | уникальность **обязана** обеспечиваться ограничением базы данных, проверки в приложении недостаточно |
| ⚠ | поле/решение не определено ТЗ — см. `open-questions.md` |
| `+` | поле, которого нет в §17 ТЗ, но оно требуется другими разделами (помечено отдельно) |

**Денежные величины.** Все стоимости — `decimal` с фиксированной точностью, не число с плавающей точкой. ТЗ оперирует долларами и двумя знаками (`$3.25`, `$4.25`, `$3.00`) → `decimal(12,2)` как рабочее ДОПУЩЕНИЕ. Валюта в ТЗ не параметризована.

**Количества.** ТЗ допускает единицы `mL` и `bottle`, но все примеры оперируют целыми числами. ДОПУЩЕНИЕ: `decimal(12,3)` для количеств, чтобы не блокировать дробные единицы; при отказе заказчика от дробных — `int`. Вопрос вынесен в `open-questions.md`.

**Время.** Все `timestamp` хранятся в UTC с указанием момента времени; отображение — в часовом поясе клиники ⚠.

## 1. Item — предмет инвентаря (§17.1)

| Поле | Тип | Обязательность | Ограничения и смысл | ТЗ |
| --- | --- | --- | --- | --- |
| `id` | id | PK | Внутренний суррогатный ключ | §17.1 |
| `internal_code` | text | NOT NULL | **U-DB**. Формат `ITM-000127`. Присваивается системой, постоянен, не переиспользуется, не редактируется через форму | §5.5, §18.5, §18.7 |
| `barcode_value` | text | NOT NULL | **U-DB**. Значение, кодируемое в штрихкод. ДОПУЩЕНИЕ: равно `internal_code` | §5.5, §18.5 |
| `name` | text | NOT NULL | Item Name — обязательное поле формы | §5.4 |
| `photo_url` | text | NULL | Ссылка на защищённый файл; прямой публичный доступ запрещён (NFR-17) | §5.4, §13, §15 |
| `sku` | text | NULL | Необязательное. Индексируется для поиска | §5.4, §5.3 |
| `reference_number` | text | NULL | Reference / Catalog Number. Индексируется для поиска | §5.4, §5.3 |
| `current_unit_cost` | decimal(12,2) | NOT NULL | ≥ 0. **Cost, не продажная цена.** Изменение влияет только на будущее | §5.4, §11.1, §5.7 |
| `unit_of_measurement` | text / enum ⚠ | NOT NULL | each, box, pack, pair, mL, bottle, roll + настраиваемые | §5.4 |
| `current_quantity` | decimal(12,3) | NOT NULL | Денормализованный остаток. **Инвариант:** равен сумме `quantity_delta` всех движений этого предмета. Может быть отрицательным, если включён соответствующий режим (FR-83) | §17.1, §10.4, §7.10 |
| `category` | text / FK ⚠ | NULL | ТЗ: «необязательное или настраиваемое поле» — справочник или свободный текст не решён | §5.4 |
| `storage_location` | text | NULL | Место хранения; используется в фильтрах | §5.4, §5.3 |
| `low_stock_threshold` | decimal(12,3) | NULL | При `current_quantity <= low_stock_threshold` — предмет в списке Low Stock | §5.4, §5.11 |
| `notes` | text | NULL | **Запрещено вносить данные пациента** (FR-133, NFR-21) | §5.4, §15 |
| `status` | enum(active, inactive) | NOT NULL | Значение по умолчанию `active`. Влияет на возможность сканирования ⚠ | §5.7, §14.4 |
| `created_at` | timestamp | NOT NULL | | §17.1 |
| `updated_at` | timestamp | NOT NULL | | §17.1 |

**Уникальность (уровень БД):**
- `UNIQUE (internal_code)` — **U-DB**. Без этого §18.5 и §21.1 «два предмета не могут получить одинаковый код» не гарантируются: проверка «код ещё не существует» (§5.5, шаг 2) в приложении подвержена гонке при параллельном создании предметов.
- `UNIQUE (barcode_value)` — **U-DB**. Отдельно от `internal_code`, даже если значения совпадают, потому что §16 запрещает «присваивать одинаковый штрихкод двум объектам».
- **Глобальная уникальность штрихкода между Item и Pack** обязана быть гарантирована. Префиксы `ITM-` / `PCK-` делают множества непересекающимися по построению, но это не ограничение БД. Рекомендуемое решение: единая таблица-реестр `BarcodeRegistry(barcode_value UNIQUE, owner_type, owner_id)`, на которую ссылаются обе сущности. При отказе от реестра — зафиксировать префиксную схему как инвариант и покрыть тестом.

**Индексы:**

| Индекс | Назначение | ТЗ |
| --- | --- | --- |
| `UNIQUE (internal_code)` | поиск по внутреннему коду при скане — самый горячий путь | §7.5, §5.3 |
| `UNIQUE (barcode_value)` | разрешение штрихкода при скане | §7.5 |
| `INDEX (sku)` | поиск | §5.3, §7.8 |
| `INDEX (reference_number)` | поиск | §5.3, §7.8 |
| Полнотекстовый/префиксный индекс по `name` | поиск по названию | §5.3, §7.8 |
| `INDEX (category)` | фильтр | §5.3 |
| `INDEX (storage_location)` | фильтр | §5.3 |
| `INDEX (status)` | скрытие неактивных | §5.7 |
| Частичный индекс `WHERE current_quantity <= low_stock_threshold` (либо `INDEX (current_quantity)`) | список Low Stock | §5.11 |

## 2. Pack — цифровой набор (§17.2)

| Поле | Тип | Обязательность | Ограничения и смысл | ТЗ |
| --- | --- | --- | --- | --- |
| `id` | id | PK | | §17.2 |
| `internal_code` | text | NOT NULL | **U-DB**. Формат `PCK-000015`. Постоянен | §6.3, §18.6 |
| `barcode_value` | text | NOT NULL | **U-DB** + уникальность в общем пространстве с Item | §6.2, §18.6 |
| `name` | text | NOT NULL | | §6.2, §6.3 |
| `photo_url` | text | NULL | | §6.2 |
| `notes` | text | NULL | Запрет пациентских данных | §6.2 |
| `status` | enum(active, inactive) | NOT NULL | | §6.2 |
| `created_at` | timestamp | NOT NULL | | §17.2 |
| `updated_at` | timestamp | NOT NULL | | §17.2 |

**Отсутствующее поле:** §6.2 требует «внутренний SKU **или** системный код», а §17.2 содержит только `internal_code`. ДОПУЩЕНИЕ: отдельное поле `sku` для пака не заводится; роль выполняет `internal_code`. См. `open-questions.md`.

**У пака нет поля количества на складе.** Это осознанное отсутствие: §6.5 и §18.10 — пак не является физическим складским объектом в MVP. Любое поле вида `current_quantity` в этой таблице — ошибка проектирования.

**Расчётная стоимость пака не хранится.** §6.4: она вычисляется как `Σ(Item.current_unit_cost × PackItem.quantity)` в момент отображения. Хранение денормализованного значения приведёт к рассинхронизации при изменении цены предмета.

**Индексы:** `UNIQUE (internal_code)`, `UNIQUE (barcode_value)`, `INDEX (status)`, индекс по `name` для поиска.

## 3. PackItem — состав пака (§17.3)

| Поле | Тип | Обязательность | Ограничения и смысл | ТЗ |
| --- | --- | --- | --- | --- |
| `pack_id` | FK → Pack.id | NOT NULL | Каскад при удалении пака ⚠ (удаление паков ТЗ не предусматривает — только `status = inactive`) | §17.3 |
| `item_id` | FK → Item.id | NOT NULL | | §17.3 |
| `quantity` | decimal(12,3) | NOT NULL | > 0 | §6.1, §17.3 |

**Уникальность:** `UNIQUE (pack_id, item_id)` — один предмет входит в пак ровно одной строкой с суммарным количеством. Иначе сканирование пака породит две строки по одному предмету, и §21.3 «остатки каждого предмета уменьшаются на правильное количество» станет неоднозначным.

**Индексы:** `INDEX (item_id)` — обратный поиск «в каких паках участвует предмет» (§6.5: один предмет может входить в несколько паков).

**Ключевой инвариант:** изменение строк `PackItem` **не порождает движений остатков** и **не трогает** уже существующие `OperationItem` (§6.7, §18.17). Состав пака читается только в момент сканирования.

## 4. Operation — операция (§17.4)

| Поле | Тип | Обязательность | Ограничения и смысл | ТЗ |
| --- | --- | --- | --- | --- |
| `id` | id | PK | | §17.4 |
| `random_case_code` | text | NOT NULL | **U-DB**. Случайный код, пример `K7P4Q`. **Не** код пациента, **не** Symplast Patient Code, **не** производный от данных пациента | §7.3, §18.4 |
| `status` | enum(Active, Finished, Voided) | NOT NULL | Начальное значение `Active` | §9, §17.4 |
| `procedure_category` | text / FK ⚠ | NULL | Обобщённая категория. **Не должна раскрывать сведения о пациенте** (§2.4) | §7.3, §17.4, §22.2 |
| `created_at` | timestamp | NOT NULL | | §17.4 |
| `finished_at` | timestamp | NULL | Заполняется только при переходе в Finished | §9.2 |
| `voided_at` | timestamp | NULL | Заполняется только при переходе в Voided | §9.3 |
| `void_reason` | text | NULL | Необязательная причина. Запрет пациентских данных | §9.3 |
| `total_cost_snapshot` | decimal(12,2) | NULL | Зафиксированный итог. ДОПУЩЕНИЕ: заполняется в момент Finish; для Active итог вычисляется как `Σ OperationItem.line_total` | §11.5, §17.4 |

**Запрещённые поля:** `patient_id`, любой Symplast-код, ФИО, дата рождения, адрес, телефон, номер карты (§2.4, §17.4, §18.3). Отдельная таблица сопоставления операции с пациентом запрещена (§7.3).

**Ограничения целостности (проверяются на уровне БД check-констрейнтами, где возможно):**
- `status = 'Finished'` ⇒ `finished_at IS NOT NULL`
- `status = 'Voided'` ⇒ `voided_at IS NOT NULL`
- `status = 'Active'` ⇒ `finished_at IS NULL AND voided_at IS NULL`
- Переход в `Voided` из `Voided` невозможен (см. `state-machines.md`)

**Индексы:**

| Индекс | Назначение |
| --- | --- |
| `UNIQUE (random_case_code)` | поиск операции по коду, гарантия неповторяемости |
| `INDEX (status, created_at DESC)` | блок активных операций и история; основной запрос списка (§7.2) |
| `INDEX (created_at DESC)` | сортировка истории |
| `INDEX (procedure_category)` | фильтр по категории (§7.2) |

**Отсутствующие поля (§17 не содержит, но требуются другими разделами):**
- `+ created_by`, `+ finished_by`, `+ voided_by` — §15 требует журнал критических действий. При двух общих аккаунтах эти поля хранят только роль/аккаунт, не персону. См. `open-questions.md`.
- `+ updated_at` — для отслеживания «последней активности», хотя ТЗ этого не требует.

## 5. OperationItem — строка операции со снимком (§17.5)

| Поле | Тип | Обязательность | Ограничения и смысл | ТЗ |
| --- | --- | --- | --- | --- |
| `id` | id | PK | | §17.5 |
| `operation_id` | FK → Operation.id | NOT NULL | | §17.5 |
| `item_id` | FK → Item.id | NOT NULL | Только для внутренней связи; отображаемые данные берутся из снимков | §17.5 |
| `source_type` | enum(individual, pack) | NOT NULL | Источник добавления. Отображается в карточке операции | §7.7, §12.2, §17.5 |
| `source_pack_id` | FK → Pack.id | NULL | Обязательно при `source_type = pack`; NULL при `individual` | §17.5 |
| `item_name_snapshot` | text | NOT NULL | Название предмета **на момент добавления** | §11.2 |
| `internal_code_snapshot` | text | NOT NULL | Внутренний код на момент добавления | §11.2 |
| `sku_snapshot` | text | NULL | SKU на момент добавления | §11.2 |
| `reference_number_snapshot` | text | NULL | Reference number на момент добавления | §11.2 |
| `quantity` | decimal(12,3) | NOT NULL | Фактически использованное количество | §11.2 |
| `unit_cost_snapshot` | decimal(12,2) | NOT NULL | **Стоимость единицы на момент добавления.** Никогда не пересчитывается | §11.2, §11.4, §18.15 |
| `line_total` | decimal(12,2) | NOT NULL | `= quantity × unit_cost_snapshot`. Хранится, а не вычисляется на лету, потому что является частью зафиксированной истории | §11.2 |
| `created_at` | timestamp | NOT NULL | | §17.5 |
| `updated_at` | timestamp | NOT NULL | | §17.5 |

**Отсутствующее поле:** `unit_of_measurement_snapshot` — §11.2 его не перечисляет, но сводка для Symplast (§12.3) показывает `quantity used`, а единица измерения может измениться в карточке предмета. ДОПУЩЕНИЕ: добавить снимок единицы измерения. См. `open-questions.md`.

**Ключевое проектное решение — гранулярность строк.** ТЗ противоречиво: §7.6 «система не обязана создавать отдельную строку» при повторном скане, но §7.7/§12.2/§17.5 требуют видеть, какие позиции добавлены через пак. Если сливать строки, источник теряется.

ДОПУЩЕНИЕ: ключ агрегации — `(operation_id, item_id, source_type, source_pack_id)`.
- Повторный скан того же предмета отдельно → та же строка, `quantity += 1`.
- Тот же предмет из пака → **отдельная** строка с `source_type = pack`.
- Один и тот же предмет из двух разных паков → две строки.

`UNIQUE (operation_id, item_id, source_type, source_pack_id)` — обеспечивает предсказуемость и делает добавление идемпотентным по ключу.

**Индексы:**

| Индекс | Назначение |
| --- | --- |
| `INDEX (operation_id)` | загрузка экрана операции и карточки истории — самый частый запрос |
| `UNIQUE (operation_id, item_id, source_type, source_pack_id)` | правило агрегации строк |
| `INDEX (item_id)` | отчёт «наиболее используемые предметы» (V2), трассировка предмета по операциям |
| `INDEX (source_pack_id)` | «в каких операциях использовался пак» |

**Инварианты:**
- `line_total = quantity × unit_cost_snapshot` (проверяется check-констрейнтом или тестом).
- Строки операции в статусах `Finished` и `Voided` **неизменяемы**: любая запись отклоняется на уровне бизнес-логики (§9.2, §11.3).
- Снимки никогда не обновляются от источника: изменение `Item.name` / `Item.current_unit_cost` не порождает UPDATE в `OperationItem` (§11.3, §18.16).

## 6. InventoryMovement — движение остатка (§17.6)

Центральная таблица учёта. Единственный способ изменить остаток.

| Поле | Тип | Обязательность | Ограничения и смысл | ТЗ |
| --- | --- | --- | --- | --- |
| `id` | id | PK | | §17.6 |
| `item_id` | FK → Item.id | NOT NULL | Движения по паку не существуют — пак не имеет остатка | §17.6, §6.5 |
| `movement_type` | enum | NOT NULL | `received`, `used_in_operation`, `returned_from_operation`, `manual_adjustment`, `inventory_count_correction`, `void_reversal` | §10.4 |
| `quantity_delta` | decimal(12,3) | NOT NULL | ≠ 0. Знак определяет направление (см. `state-machines.md`) | §17.6 |
| `operation_id` | FK → Operation.id | NULL | Обязательно для `used_in_operation`, `returned_from_operation`, `void_reversal`; NULL для остальных | §17.6 |
| `reason` | text / enum | NULL | Обязательно для `manual_adjustment` (§5.9). Значения: damaged, expired, missing, inventory correction, received outside normal process, other | §5.9, §17.6 |
| `idempotency_key` | text | NOT NULL | **U-DB**. Ключ, гарантирующий однократное применение | §10.4, §16 |
| `created_at` | timestamp | NOT NULL | | §17.6 |

### `idempotency_key` — почему только БД

§10.4: «Каждое движение должно иметь уникальный идентификатор, чтобы повторная отправка запроса не списала и не вернула предмет дважды». §16 запрещает двойное списание и двойной возврат.

Проверка «а нет ли уже такого ключа?» в коде приложения **не решает задачу**: два параллельных запроса (двойной клик, ретрай после таймаута, повторная отправка очереди offline-синхронизации) одновременно пройдут проверку и оба вставят движение. Единственная надёжная защита — `UNIQUE (idempotency_key)` в базе: второй INSERT падает, обработчик перехватывает нарушение уникальности и возвращает результат первой операции как успешный (а не ошибку пользователю).

**Формирование ключа (ДОПУЩЕНИЕ, ТЗ не задаёт):**

| Событие | Состав ключа |
| --- | --- |
| Скан / ручное добавление в операции | `op:{operation_id}:scan:{client_event_id}` — `client_event_id` генерируется клиентом при нажатии/скане и переживает ретраи |
| Изменение количества строки | `op:{operation_id}:line:{operation_item_id}:rev:{revision}` |
| Undo | `op:{operation_id}:undo:{client_event_id}` |
| Позиция пака при скане пака | `op:{operation_id}:pack:{client_event_id}:item:{item_id}` |
| Receive Stock | `receive:{client_event_id}` |
| Ручная корректировка | `adjust:{client_event_id}` |
| Строка инвентаризации | `count:{count_id}:item:{item_id}` |
| Void | `void:{operation_id}:item:{item_id}` — детерминированный, **не** содержит случайной части. Это и есть машинная гарантия того, что повторный Void не вернёт остатки второй раз (§9.3, §18.21) |

**Индексы:**

| Индекс | Назначение |
| --- | --- |
| `UNIQUE (idempotency_key)` | **U-DB**, защита от двойного применения |
| `INDEX (item_id, created_at)` | история движений предмета, пересчёт/сверка остатка |
| `INDEX (operation_id)` | расчёт «сколько эта операция списала» для Void — критичный путь §10.3 |
| `INDEX (operation_id, item_id, movement_type)` | вычисление чистого списания по предмету в операции |
| `INDEX (movement_type, created_at)` | отчётность, аудит |

**Инварианты:**
- `Item.current_quantity == Σ InventoryMovement.quantity_delta WHERE item_id = ...` — сверяемо регламентной проверкой.
- Запись движения и обновление `Item.current_quantity` происходят в одной транзакции (§16).
- Для операции существует **не более одного набора** движений `void_reversal` (гарантия — детерминированный `idempotency_key`).

## 7. UserAccount — учётная запись (§17.7)

| Поле | Тип | Обязательность | Ограничения и смысл | ТЗ |
| --- | --- | --- | --- | --- |
| `id` | id | PK | | §17.7 |
| `username` | text | NOT NULL | **U-DB** | §3.1, §17.7 |
| `password_hash` | text | NOT NULL | Только необратимый хеш. Пароль в открытом виде не хранится нигде | §3.1, §15 |
| `role` | enum(Staff, Admin) | NOT NULL | Определяет права; проверяется на сервере при каждом запросе | §2.3, §3.2, §3.3, §18.1 |
| `active` | bool | NOT NULL | | §17.7 |
| `updated_at` | timestamp | NOT NULL | | §17.7 |

**Отсутствующие поля** (§17.7 их не содержит, но они нужны для §3.1/§15): `+ created_at`, `+ last_login_at`, `+ failed_login_count`, `+ locked_until`. Без последних двух ограничение попыток входа (FR-5, NFR-15) реализуется только во внешнем слое (кеш/прокси). См. `open-questions.md`.

**Ограничение:** в системе ровно два аккаунта — интерфейс не предоставляет создания третьего (§18.1). Ограничение уровня БД («не более одной записи на роль») ТЗ не требует, но проверка при создании обязательна.

## 8. Сущности, требуемые ТЗ, но отсутствующие в §17

Эти таблицы **не описаны** в разделе 17, однако без них требования других разделов невыполнимы. Внесены как ДОПУЩЕНИЯ, детально — в `open-questions.md`.

### 8.1. InventoryCount / InventoryCountLine (нужно для §5.10)

§5.10 требует, чтобы незавершённая инвентаризация сохранялась при обновлении страницы. Значит, она не может жить в памяти браузера.

| Сущность | Поля |
| --- | --- |
| `InventoryCount` | `id`, `status` (draft / applied / cancelled ⚠), `created_at`, `applied_at`, `notes` |
| `InventoryCountLine` | `id`, `count_id` FK, `item_id` FK, `expected_quantity` (снимок ожидаемого на момент ввода), `counted_quantity`, `difference`, `applied` bool, `created_at`. `UNIQUE (count_id, item_id)` |

При подтверждении каждая строка порождает движение `inventory_count_correction` с `quantity_delta = counted − expected` и ключом `count:{count_id}:item:{item_id}`.

### 8.2. SystemSetting (нужно для §3.2, §7.10, §3.3)

Требуются как минимум две настройки: показывать ли Staff себестоимость (§3.2, §7.4, §22.1) и режим поведения при нехватке остатка (§7.10, §22.4). §3.3 упоминает «управлять основными настройками», но перечня настроек ТЗ не даёт.

| Поле | Тип |
| --- | --- |
| `key` | text, **U-DB** |
| `value` | text / json |
| `updated_at` | timestamp |

### 8.3. AuditLog (нужно для §15)

§15 требует «журнал критических системных действий», но сущности в §17 нет и перечень критических действий не задан. Минимальный состав: `id`, `actor_account_id`, `actor_role`, `action`, `entity_type`, `entity_id`, `payload_summary` (без пациентских данных), `created_at`. Индексы: `(created_at DESC)`, `(entity_type, entity_id)`.

### 8.4. OperationEvent (возможно нужно для §7.6)

§7.6: «каждое сканирование должно сохраняться в истории действий активной операции». Частично покрывается `InventoryMovement` (у каждого скана есть движение), но действия без движения (изменение категории, попытка скана неизвестного кода) там не отражаются. Решение о заведении отдельного журнала событий операции — открытый вопрос.

## 9. Сводная схема связей

```
UserAccount (Staff | Admin)
      │ (роль проверяется на сервере; в §17 нет FK от операций к аккаунту)
      ▼
Operation ──1───n── OperationItem ──n───1── Item
    │ status: Active/Finished/Voided      ▲       │
    │                                     │       │ 1
    │                                     │       │
    │                            source_pack_id   n
    │                                     │   InventoryMovement
    │                                     │       ▲
    │                                     │       │ operation_id (nullable)
    └─────────────────────────────────────┼───────┘
                                          │
                                        Pack ──1───n── PackItem ──n───1── Item
                                     (нет остатка,
                                      нет хранимой стоимости)
```

## 10. Сводка обязательных ограничений уровня БД

| Ограничение | Сущность | Почему приложения недостаточно | ТЗ |
| --- | --- | --- | --- |
| `UNIQUE (internal_code)` | Item | §5.5 предписывает проверку «код не существует» в приложении; при параллельном создании двух предметов обе проверки пройдут и выдадут одинаковый код. §21.1 требует, чтобы это было невозможно | §5.5, §18.5, §21.1 |
| `UNIQUE (barcode_value)` | Item | §16: «не присваивать одинаковый штрихкод двум объектам» — это инвариант данных, а не поведения UI | §16 |
| `UNIQUE (internal_code)` | Pack | То же для паков | §6.3, §18.6 |
| `UNIQUE (barcode_value)` | Pack | То же; плюс требуется непересечение пространства кодов Item и Pack | §16, §18.6 |
| `UNIQUE (idempotency_key)` | InventoryMovement | Единственная защита от гонки при двойном клике, ретрае после таймаута и повторной отправке очереди offline. Проверка «уже есть?» в коде не атомарна | §10.4, §16, §8.4 |
| `UNIQUE (random_case_code)` | Operation | Код генерируется случайно; без ограничения БД коллизия останется незамеченной | §7.3 |
| `UNIQUE (username)` | UserAccount | Базовая целостность аутентификации | §3.1 |
| `UNIQUE (pack_id, item_id)` | PackItem | Иначе состав пака неоднозначен и §21.3 непроверяем | §6.1 |
| `UNIQUE (operation_id, item_id, source_type, source_pack_id)` | OperationItem | Правило агрегации строк; делает добавление предсказуемым | §7.6, §7.7 |
| `UNIQUE (count_id, item_id)` | InventoryCountLine | Одна строка инвентаризации на предмет | §5.10 |
| `UNIQUE (key)` | SystemSetting | | §3.3 |

Дополнительно: все изменения остатка (`INSERT` в `InventoryMovement` + `UPDATE Item.current_quantity`) — в одной транзакции; при сканировании пака вся группа позиций — в одной транзакции (§16).
