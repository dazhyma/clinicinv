# Технические решения

Журнал решений, принятых при реализации. Источник истины по требованиям —
`Clinic_Inventory_System_TZ_RU.md`; открытые вопросы к заказчику — `open-questions.md`.
Здесь фиксируется только то, **как** реализовано и **почему** именно так.

Формат: решение → основание в ТЗ → что придётся менять, если заказчик решит иначе.

---

## D-1. Деньги — целые центы (`INTEGER`)

Все денежные величины хранятся целым числом центов: `current_unit_cost_cents`,
`unit_cost_snapshot_cents`, `line_total_cents`, `total_cost_snapshot_cents`,
`unit_cost_at_receipt_cents`. Ни одного столбца `REAL` для сумм в схеме нет.
Форматирование в доллары — только на слое представления (`formatCents`).

**Основание.** §11 требует точной себестоимости, §16 — целостности данных.
Двоичная плавающая точка не представляет 0.1 точно; в учётной системе это
даёт расхождения в итогах, которые невозможно объяснить пользователю.

**Побочный эффект.** Округления при расчёте строки не возникает вовсе:
`line_total_cents = quantity (целое) × unit_cost_snapshot_cents (целое)` —
точное целое. Это строже, чем требование Q-23 «округлять half-up на уровне строки»,
и делает итог операции воспроизводимым при любом пересчёте.

**Валюта** одна и не параметризована (Q-23) — как в ТЗ.

## D-2. Количества — целые числа (`INTEGER`) — ДОПУЩЕНИЕ

Все количества целые: `current_quantity`, `quantity_delta`, `quantity`,
`expected_quantity`, `counted_quantity`, `low_stock_threshold`.

**Основание.** Все примеры ТЗ целочисленные (10, 147, 2, 20, 6, 97),
сканирование по природе даёт «+1». Инвариант
`current_quantity == SUM(quantity_delta)` проверяется на точное равенство —
с целыми это надёжно, с дробными потребовало бы допуска сравнения.

**Расхождение с аналитиком.** `data-model.md` предлагает `decimal(12,3)` (Q-12),
чтобы не блокировать `mL` и `bottle`. Решение принято в пользу целых:
дробный объём учитывается выбором единицы измерения («1 bottle», а не «0.5 bottle»).

**Цена изменения.** Если заказчик потребует дробные количества, менять придётся
тип столбцов во всех таблицах движений и строк операций плюс сравнение
инварианта. Это миграция данных, а не переписывание логики. **Вопрос вынесен
заказчику как приоритетный** (см. `open-questions.md`, вопрос №4).

Допущение зафиксировано комментарием в коде: `src/domain/quantity.ts`.

## D-3. Единственный способ изменить остаток — движение

`items.current_quantity` изменяется только функцией `applyMovement()`
(`src/domain/movements.ts`), которая в одной транзакции пишет строку
`inventory_movements` и сдвигает остаток. Прямой `UPDATE` остатка в коде
отсутствует; `updateItem()` явно отвергает попытку передать `currentQuantity`.

**Основание.** §10.4: журнал движений предотвращает неправильный пересчёт
при изменениях, совершённых после операции. Без него Void «ровно на списанное»
(§10.3) невычислим в принципе.

Инвариант покрыт тестом `findStockInvariantMismatches()` и проверяется в
каждом сценарии тестов, меняющем остаток.

## D-4. Седьмой тип движения — `initial`

§10.4 перечисляет шесть типов. Добавлен седьмой — `initial` — для начального
количества при создании предмета.

**Основание.** Противоречие C-13: §5.4 делает `Initial Quantity` обязательным
полем, но §10.4 не называет для него тип движения. Если записать начальное
количество прямо в `current_quantity`, инвариант D-3 ломается на первом же
предмете и сверка склада становится невозможной.

**Расхождение с аналитиком.** `state-machines.md` §2.2 предлагает использовать
`received` с `reason = "initial stock"`. Выбран отдельный тип: «поставка» и
«первичное заведение остатка» — разные события, и в отчёте по поставкам
(будущий FIFO из Q-9) их придётся разделять. Ключ идемпотентности
`init:{item_id}` детерминирован, поэтому повторное создание невозможно.

При `Initial Quantity = 0` движение не создаётся.

## D-5. Ключ агрегации строки операции включает цену

`UNIQUE (operation_id, item_id, source_type, COALESCE(source_pack_id, 0), unit_cost_snapshot_cents)`

**Основание.** Аналитик предложил ключ без цены (Q-15). Но тогда добавление
предмета после изменения его текущей стоимости даёт неразрешимый выбор:
либо переписать `unit_cost_snapshot` существующей строки (прямое нарушение
§18.15 и §11.4 «уже добавленные строки не должны самопроизвольно изменяться»),
либо применить к новой единице старую цену (нарушение §11.4 «применяется
стоимость, действующая на момент нового добавления»).

Включение цены в ключ выполняет оба требования: повторный скан при неизменной
цене наращивает ту же строку (§7.6), а после изменения цены появляется отдельная
строка с новым снимком. Покрыто тестом в `tests/cost-snapshot.test.ts`.

`COALESCE(source_pack_id, 0)` обязателен: в SQLite NULL-значения в уникальном
индексе считаются различными, и без него две строки `individual` прошли бы проверку.

## D-6. Глобальный реестр штрихкодов вместо соглашения о префиксах

Таблица `barcode_registry (barcode_value PRIMARY KEY, owner_type, owner_id)`.
Предмет и пак регистрируют штрихкод в той же транзакции, где создаются.

**Основание.** §16 запрещает «присваивать одинаковый штрихкод двум объектам».
Префиксы `ITM-`/`PCK-` делают множества непересекающимися по построению, но
это соглашение в коде, а не ограничение БД, и §21.1 требует невозможности
дубликата. Строки из реестра не удаляются никогда — код не переиспользуется (§5.5).

FK из `items`/`packs` в реестр не ставится: он потребовал бы вставлять строку
реестра до появления `owner_id`, то есть с заглушкой. Регистрация в одной
транзакции даёт ту же гарантию без заглушки.

## D-7. Номера кодов — из счётчика, а не из `COUNT(*)`

Таблица `code_sequences (prefix, next_value)`; номер выдаётся
`UPDATE ... RETURNING` внутри транзакции `BEGIN IMMEDIATE`, в которой создаётся
объект.

**Основание.** §5.5 предписывает проверку «код ещё не существует» в приложении,
но при параллельном создании две проверки пройдут одновременно (AC-1.5, шаг 2).
Писательская блокировка SQLite сериализует выдачу номеров, а уникальный индекс
на `internal_code` — вторая линия защиты. `COUNT(*)` непригоден: после
деактивации объектов он выдал бы занятый номер (Q-14).

Формат — 6 цифр (`ITM-000127`), как в ТЗ.

## D-8. Все изменения остатка — в `BEGIN IMMEDIATE`

`runInTransaction()` открывает транзакцию с `behavior: 'immediate'`.

**Основание.** §16 требует атомарности. `deferred` (по умолчанию) берёт
писательскую блокировку лениво: два параллельных сканирования успели бы
прочитать один и тот же остаток и получить `SQLITE_BUSY` при апгрейде
блокировки — посреди уже начатой операции. `immediate` берёт блокировку сразу.
Плюс `busy_timeout = 5000` на соединение.

Скан пака выполняется одной транзакцией на весь состав: «половина пака»
физически невозможна (§16, AC-3.2).

## D-9. Миграции — рукописный SQL, схема Drizzle — типизированное отражение

`drizzle/*.sql` применяются собственным раннером (`src/db/migrate.ts`) с учётом
в таблице `schema_migrations`. `src/db/schema.ts` описывает те же таблицы для
типобезопасных запросов.

**Основание.** Схеме нужны CHECK-констрейнты (`line_total = quantity × unit_cost`,
`quantity_delta <> 0`, согласованность статуса и меток времени операции) и
уникальный индекс по выражению `COALESCE(source_pack_id, 0)`. В декларативном
описании Drizzle это не выражается, а именно эти ограничения держат
критические правила §18.

**Риск.** Схема и SQL могут разойтись. Закрыт тестом `tests/schema.test.ts`:
для каждой таблицы из `schema.ts` сверяется наличие всех столбцов в реальной БД.

## D-10. Проверка роли — и в HTTP-слое, и в домене

`requireActor()`/`requireAdmin()` в `src/auth/guards.ts` плюс `assertAdmin()`
внутри каждого административного доменного сервиса.

**Основание.** §15 и AC-6.2 (шаг 11) требуют, чтобы Admin-действие, вызванное
из-под Staff напрямую, было отклонено. Двойная проверка означает, что забытый
guard в новом маршруте не открывает дыру. Тесты `tests/access.test.ts` вызывают
доменные сервисы напрямую, минуя HTTP, — это и есть модель атаки.

---

## D-11. Middleware — не рубеж безопасности

`src/middleware.ts` проверяет только наличие cookie и делает редирект.

**Основание.** Middleware исполняется в Edge-рантайме, где недоступен
`better-sqlite3`; проверить, что сессия не отозвана и не истекла, там нельзя.
Настоящая проверка — `validateSessionToken()` на каждом запросе в серверных
компонентах и обработчиках. Middleware — удобство навигации.

## D-12. Блокировка входа по паре (username, IP)

5 неудач → 15 минут, параметры в `.env`. Есть ручное снятие (`clearLoginLock`).

**Основание.** Q-36. Аккаунтов в системе всего два и они общие на всю клинику
(§2.3). Блокировка учётной записи `staff` целиком остановила бы операционную —
это прямая угроза сценарию §23. Блокировка по паре останавливает подбор с
конкретного адреса, не задевая остальные устройства. Покрыто тестом.

---

## D-13. Undo откатывает последнее добавляющее событие целиком

Журнал `operation_events` хранит каждое добавление с `payload_json`, содержащим
затронутые строки. `undoLastScan()` откатывает последнее событие с
`undoable = 1`.

**Основание.** Q-27. Скан пака откатывается полностью: частичный откат нарушил
бы §16 «нельзя списать половину пака» в обратную сторону. Глубина — один шаг
(кнопка называется «Undo Last Scan»). Ручные изменения количества через Undo
не откатываются — для них есть `+`/`−`.

**Собственное допущение сверх Q-27.** Если после скана количество строки уже
уменьшали вручную, возвращается не больше, чем в строке осталось: иначе
операция вернула бы на склад больше, чем реально забрала, и инвариант D-3
показал бы расхождение.

## D-14. Void фиксирует итог и у активной операции

При Void операции в статусе `Active` в `total_cost_snapshot_cents` записывается
текущая сумма строк.

**Основание.** §9.3 и AC-9.6: аннулированная операция сохраняется в истории со
строками и итогом, но исключается из финансовых агрегатов. У активной операции
снимка ещё нет, а после Void состав уже неизменяем — значит, момент фиксации
единственный. Исключение из агрегатов обеспечивается фильтром
`status = 'Finished'` в `totalCostForFinishedOperations()`.

## D-15. Хранение времени — unix-миллисекунды UTC

Столбцы времени — `INTEGER`, отображаются в часовом поясе клиники на слое
представления (Q-26). Огрубление до периода (Q-3) — настройка отображения,
не изменение схемы.

## D-16. Слой действий вынесен из `src/app` — `src/actions/*`

Валидация формы, проверка роли и превращение доменной ошибки в сообщение
экрана живут в `src/actions/*` — обычных функциях вида
`action(db, actor, input)`. В `src/app/**/actions.ts` остаются только тонкие
`'use server'`-обёртки: сессия, разбор `FormData`, загрузка файла,
`revalidatePath`, `redirect`.

**Основание.** Модуль с `'use server'` тянет `next/headers` и `next/cache`,
которые вне HTTP-запроса не работают: протестировать «Staff вызвал
Admin-действие напрямую» в таком модуле нельзя, не поднимая сервер. Требование
проверять роль на сервере (§18.22, AC-6.2 шаг 11) должно быть покрыто
исполняемым тестом, а не ревью. `tests/actions.test.ts` вызывает эти функции
напрямую — это и есть модель атаки.

Бизнес-логики остатков в слое действий нет: движения, идемпотентность,
снимки стоимости и транзакции остаются в `src/domain/*`.

## D-17. Сырой ввод формы валидируется в слое действий, а не в обёртке

Действия принимают строки (`costPerUnit: '3.25'`, `initialQuantity: '0'`), а не
уже разобранные числа. Разбор и накопление ошибок по полям — `FieldValidator`
(`src/actions/parse.ts`).

**Основание.** §5.4 делает `Initial Quantity` обязательным полем, но допускает
значение 0. Если преобразовать ввод в число до валидации, пустое поле и «0»
станут неразличимы и незаполненная форма молча сохранится с нулевым остатком.
Различие проверяется тестом.

Побочный эффект: ошибки привязаны к конкретным полям (`aria-describedby`,
`aria-invalid`), а не выводятся общим списком.

## D-18. Себестоимость режется на сервере отсутствием поля, а не значением

`toItemView()` не кладёт `unitCostCents` и `unitCostFormatted` в объект вовсе,
когда актор — Staff и `staff_can_see_cost = false`. Не `null`, не пустая
строка, не скрытие в CSS.

**Основание.** §3.2 и Q-1: «в ответ Staff-сессии финансовые поля не попадают
вовсе». Проверяемое свойство `'unitCostCents' in view === false` невозможно
подделать разметкой; значение `null` в том же поле было бы неотличимо от
«стоимость не заполнена» и однажды просочилось бы в разметку.

Тест: `tests/actions.test.ts`, блок «Себестоимость для Staff».

## D-19. Фотографии — вне `public/`, отдаются маршрутом с проверкой сессии

Файлы пишутся в `UPLOADS_DIR` (по умолчанию `./data/uploads`, каталог `data/`
уже в `.gitignore`). В `items.photo_url` хранится не путь к файлу, а URL
маршрута `/api/photos/<token>`; сам маршрут на каждом запросе вызывает
`requireActor()` и без сессии отдаёт 401.

**Основание.** §15 и NFR-17: «отсутствие публичных URL, через которые можно
просмотреть инвентарь без входа» и «защита загруженных файлов». Любой файл в
`public/` раздаётся статикой мимо middleware и мимо guard'ов — это прямое
нарушение, которое невозможно исправить настройкой.

Следствия:
- `next/image` используется с `unoptimized`: оптимизатор Next ходит за
  картинкой собственным запросом без cookie и получил бы 401;
- имя файла — 32 hex-символа, поэтому выход за каталог через `../` невозможен
  по построению (проверено тестом);
- фото-модуль разделён на `shared.ts` (константы и разбор URL, попадает в
  клиентский бандл) и `storage.ts` (`sharp`, `node:fs`, только сервер).

## D-20. Тип загружаемого файла определяется по содержимому

`storeItemPhoto()` отдаёт буфер в `sharp().metadata()` и принимает только
`jpeg` / `png` / `webp`. Расширение файла и `Content-Type` из формы не
используются как проверка — только как подсказка браузеру (`accept`).

**Основание.** §13 перечисляет форматы, §15 требует защиты загруженных файлов.
Расширение и MIME-тип подделываются тривиально; переименованный скрипт с
расширением `.png` прошёл бы проверку по имени. Тест загружает текстовый файл
под именем `evil.png` и ожидает отказ.

Q-40: хранится уменьшенная версия (максимальная сторона 1024 px) и миниатюра
256 px для списка — §13 требует, чтобы фотографии не замедляли работу.

---

## D-21. Ключ идемпотентности генерируется в форме и живёт до успеха

Клиентские формы Receive Stock и корректировки держат `clientEventId` в
состоянии и меняют его ТОЛЬКО после подтверждённого успеха
(`src/app/inventory/_components/stock-forms.tsx`).

**Основание.** §10.4 и §16: повторная отправка запроса не должна списать или
вернуть предмет дважды. Блокировка кнопки на время запроса от этого не
защищает — ретрай после сетевого таймаута уходит уже после разблокировки.
Гарантию даёт уникальный индекс `ux_inventory_movements_idempotency`; форма
лишь обязана прислать тот же ключ.

Повтор возвращается пользователю как **успех** с пометкой «уже записано», а не
как ошибка: иначе персонал решит, что поставка не прошла, и введёт её заново.

## D-22. Поиск экранирует служебные символы LIKE

`listItems()` экранирует `%`, `_` и `\` и передаёт `escape '\'`.

**Основание.** Поиск работает по названию, Item Code и reference number. Без
экранирования запрос «70%» превратился бы в шаблон «всё
подряд», а «REF_11» молча нашёл бы лишнее. В учётной системе тихо неверная
выборка хуже пустой. Покрыто тестом.

## D-23. Настройки в интерфейсе ограничены двумя ключами

Страница `/settings` в этом спринте меняет только `staff_can_see_cost` и
`negative_stock_mode`.

**Основание.** §4 требует кнопку Settings для Admin, а мёртвая ссылка —
дефект. Оба ключа управляют поведением, которое уже реализовано и проверяется
тестами. Остальные ключи (`sound_on_scan_enabled`, `label_size_preset`,
`procedure_category_enabled`) появятся вместе с экранами, которые их читают:
настройка без потребителя непроверяема.

## D-24. Человекочитаемая строка этикетки — элемент `<text>`, а не контуры глифов

`renderLabelSvg()` (`src/domain/barcode.ts`) собирает этикетку сам: штрихкод
рисуется bwip-js с `includetext: false` и вкладывается во внешний SVG, а код
печатается настоящим `<text>`.

**Основание.** §5.5 требует читаемую человеком строку под графическим кодом.
bwip-js с `includetext: true` выводит её контурами шрифта: в разметке текста нет,
скринридер молчит, а проверить требование можно только сравнением картинок.
С `<text>` строка есть в разметке (`>ITM-000127</text>`), доступна скринридеру
через `aria-label` и покрыта тестом.

Растровый PNG (`Download PNG`) — исключение: там выбирать не из чего, текст
рисует bwip-js.

**Побочный эффект.** Внешний SVG задаёт свободное поле по краям (quiet zone),
которого у «голой» графики bwip-js нет, — сканеру нужны пустые поля слева и
справа от кода.

---

## D-25. Страница печати не подключает общую шапку вообще

`/inventory/items/[id]/barcode` и `/inventory/packs/[id]/barcode` не рендерят
`AppHeader` и вкладки. Скрывается через `@media print` только блок управления
(копии, размер, Print, скачивание) — класс `no-print`.

**Основание.** §5.6 перечисляет, чего на печатной странице быть не должно:
навигационное меню, лишние кнопки, фоновые элементы, карточка предмета.
Скрытие печатью — механизм для элементов, которые нужны на экране (выбор копий).
Для навигации механизм не нужен: её просто нет, и никакая ошибка в CSS не
вынесет её на бумагу.

Печать N копий — повторение одного и того же SVG в потоке (`.label-sheet`),
поэтому «печать на обычном листе» получается сама собой при любом размере
этикетки, а отдельного режима «A4 сеткой» не требуется.

## D-26. Стоимость пака нигде не хранится и не вводится

В таблице `packs` нет ни одного столбца стоимости (проверяется тестом), в
`PackForm` нет поля итоговой суммы, `PackView.costCents` вычисляется в момент
чтения из текущих цен предметов.

**Основание.** §6.4: «Стоимость пака не вводится вручную как независимая сумма»,
«при изменении текущей стоимости предмета текущая расчётная стоимость пака
обновляется». Хранимое значение неизбежно разошлось бы с ценами предметов —
и никакой триггер это не чинит, потому что «правильное» значение зависит от
момента чтения.

На историю это не влияет никак: строки завершённых операций держат собственные
снимки (§11.2, D-5), и код отображения к ним не прикасается.

Форма показывает тот же расчёт до сохранения — это подсказка, а не источник
данных: сервер считает заново.

## D-27. Скачивание этикетки — маршрут с проверкой сессии и проверкой реестра

`/api/barcode/[code]?format=svg|png` вызывает `requireActor()` и отдаёт файл
только если код найден в `barcode_registry`.

**Основание.** §15/NFR-18 запрещают публичные URL, отдающие данные инвентаря;
внутренний код — данные инвентаря. Проверка по реестру нужна отдельно: без неё
маршрут стал бы генератором штрихкодов произвольных строк, и распечатанная
этикетка могла бы нести код, которого в системе нет (§18.6 — «два объекта не
могут получить одинаковый штрихкод» — держится реестром, D-6).

Для показа на экране маршрут не используется: SVG рендерится прямо в разметке
страницы, лишнего запроса нет.

## D-28. Пресеты размеров этикеток — константа в коде, не настройка

`src/domain/label-sizes.ts`: 50×25, 57×32, 70×37 мм; выбор делается на самой
странице печати и не сохраняется.

**Основание.** Q-5 предлагал хранить пресеты в настройках. Ключ
`label_size_preset` в `SETTING_KEYS` есть, но экрана, который бы его менял, нет
(D-23: настройка без потребителя непроверяема), а печать нужна уже сейчас.
Размеры этикеток клиники не утверждены (§22.5) — до ответа заказчика любой
«сохранённый по умолчанию» размер всё равно был бы угадан.

**Цена изменения.** Добавить пресет — одна строка массива. Привязать выбор к
настройке — чтение ключа в двух страницах печати.

---

## D-29. Строки состава пака нумеруются позицией формы

Ошибки состава привязаны к полям `component-{index}-itemId` и
`component-{index}-quantity`; серверная обёртка собирает строки из двух
параллельных `getAll()`.

**Основание.** §14.4 требует конкретных сообщений. «The same item is listed
twice in this pack» без указания строки заставляет пользователя искать дубликат
глазами; сообщение «Gauze 4x4 is already listed in row 1» подсвечивает нужное
поле. Индексы не разъезжаются, потому что каждая строка формы всегда рисует оба
поля, а `FormData.getAll()` сохраняет порядок разметки.

Полностью пустая строка игнорируется: пользователь мог нажать «Add item» лишний
раз, и превращать это в ошибку — недружелюбно.

## D-30. Каждое мутирующее действие операции возвращает ПОЛНОЕ состояние с сервера

`scanIntoOperationAction`, `addItemToOperationAction`, `changeLineQuantityAction`
и `undoLastScanAction` отдают `OperationMutationResult.state` — весь список
строк, количества, снимки цен и итог, а не дельту.

**Основание.** §14.3 требует отклика ≤500 мс, поэтому экран показывает скан
оптимистично, до ответа сервера. Если бы клиент «досчитывал» количества сам,
после отказа сервера он остался бы с состоянием, которого в БД нет, — а §8.1
запрещает держать операцию в памяти страницы. Замена состояния целиком делает
клиент производным от сервера: любое расхождение исчезает первым же ответом.

**Побочный эффект.** Ответ на более ранний запрос может прийти позже
(сканирование идёт быстрее ответов). Каждому запросу присваивается номер, и
состояние применяется, только если оно новее уже применённого, — иначе
пользователь увидел бы, как отсканированная позиция «пропадает».

---

## D-31. Оптимистичный отклик опирается на индекс «штрихкод → название»

Со страницей активной операции отдаётся `scanIndexForActor()` — список
`{barcode, kind, name, состав пака}` (до 2000 предметов).

**Основание.** Без него клиент не может назвать предмет до ответа сервера и
показал бы «…» вместо `Gauze 4x4 added`. §14.3 отводит на реакцию 500 мс,
включая сеть.

**Стоимости в индексе нет намеренно.** Она не нужна для отклика, а её попадание
в клиентский бандл Staff нарушило бы D-18 («поля стоимости отсутствуют в ответе,
а не скрыты»). Цена приходит вместе с подтверждённой строкой от сервера.

Незнакомый код не ломает сценарий: показывается нейтральное «`ITM-000127` —
checking…», которое ответом сервера превращается в зелёное подтверждение или в
красное **Barcode not found**.

---

## D-32. Ключ идемпотентности скана — новый на каждый скан (в отличие от D-21)

В формах Receive Stock и корректировки ключ живёт до подтверждённого успеха
(D-21). На операционном экране `newClientEventId()` вызывается в момент КАЖДОГО
скана и не переиспользуется.

**Основание.** Это разные события. Повторная отправка одной формы — тот же
факт поставки. Второй скан того же предмета — второй факт расхода (§7.6: «система
увеличивает его количество»). Общий ключ на два скана потерял бы вторую единицу.

Защита от двойного срабатывания сканера и ретрая при этом сохраняется:
один и тот же вызов повторяется с тем же ключом, и уникальные индексы
`ux_operation_events_client` и `ux_inventory_movements_idempotency` не дают
применить его дважды (проверено тестом «повтор возвращает результат первой
попытки»).

---

## D-33. `−`/`+` присылают абсолютное количество, а не дельту

`changeLineQuantityAction` принимает целевое количество строки; движение
считает домен.

**Основание.** В операционной по `+` нажимают быстро и несколько раз подряд.
Дельты, разошедшиеся с ответами сервера, дали бы количество, зависящее от
порядка их применения. Абсолютное значение делает последний применённый запрос
победителем, и итог совпадает с тем, что пользователь видит на экране.
Ноль эквивалентен удалению строки (Q-31).

## D-34. Поле сканирования удерживает фокус принудительно

Фокус возвращается в поле после ответа сервера, после нажатий `−`/`+`, после
закрытия ручного поиска, по `visibilitychange` и по любому касанию экрана.
Единственное исключение — открытый диалог: проверяется наличие
`[role="dialog"]` у активного элемента и у цели нажатия.

**Основание.** §7.5 прямо запрещает заставлять пользователя «нажимать в поле
перед каждым сканированием». Без исключения для диалогов поле причины Void и
строка ручного поиска теряли бы фокус после каждого клика, и набрать в них
текст было бы невозможно.

`inputMode="none"` у поля скана — **ДОПУЩЕНИЕ**: сканер клиники это
HID-устройство, экранная клавиатура планшета ему не нужна и только перекрывает
список позиций. Ручной ввод кода делается через Manual Item Search, который
ищет и по внутреннему коду (§7.8).

## D-35. Категория процедуры в интерфейсе не вводится

`operations.procedure_category` в схеме есть и отображается, если заполнена, но
ни одна форма спринта её не задаёт.

**Основание.** §2.4 запрещает хранить сведения, раскрывающие пациента, а Q-2
(закрытый справочник категорий) заказчиком не утверждён. Свободное текстовое
поле «на всякий случай» — это ровно то поле, куда персонал впишет пациента
(§18.3). До утверждения справочника поля в UI нет.

## D-36. Подтверждение скана — баннер и звук, а не диалог

Крупная зона «последний отсканированный предмет» (зелёная при успехе, красная
при ошибке) плюс синтезированный Web Audio тон. Ни одного модального окна после
успешного скана.

**Основание.** C-9: §7.5 требует крупного визуального подтверждения, §14.2
запрещает подтверждение ДЕЙСТВИЕМ. Оба требования выполняются одновременно.

Звук синтезируется, а не грузится файлом: лишний сетевой запрос в момент скана
съедает бюджет §14.3, а тон должен звучать и при мгновенном повторе. Успех и
ошибка различаются высотой и длительностью — на экран во время операции смотрят
не всегда. Любая ошибка Web Audio подавляется: §7.5 говорит «если поддерживается
устройством».

## D-37. Минимум §8.4 без локальной очереди

Экран показывает: `All changes saved`, `Saving N changes…`,
`Offline — N changes waiting to sync`, `Changes are not synced — check connection`.
Действие, не дошедшее до сервера, не сохраняется и не досылается.

**Основание.** Полноценный offline-first — раздел 20 ТЗ и в MVP не входит.
§8.4 при этом требует минимума: не терять подтверждённые сервером данные и
ясно предупреждать о несинхронизированных. Очередь-полумера была бы хуже
отсутствия очереди: она создаёт впечатление сохранности, не давая гарантий
порядка и идемпотентности при массовой досылке.

Пользователь всегда видит, ЧТО именно не сохранилось: сообщение называет
предмет («Gauze 4x4 was not saved»), молчаливого исчезновения нет (§14.4).

## D-38. Аннулированная операция для Staff не существует

`getOperationState()` возвращает `undefined` для Voided-операции под Staff, и
страница отвечает 404; список её не отдаёт.

**Основание.** §7.2 относит историю аннулированных к Admin (Q-34). Скрытие
блока в разметке защитой не является: прямая ссылка `/operations/17` должна
давать тот же результат, что и отсутствие кнопки.

## D-39. Экран завершённой и аннулированной операции — сокращённый, только чтение

Показываются статус, метки времени, позиции со снимками и итог; кнопок
изменения состава нет, для Admin есть Void.

**Основание.** Карточка завершённой операции и сводка для Symplast — §12 и
следующий спринт. Но ссылка «View» из истории обязана вести не в пустоту, а
Void по §9.3 доступен и для Finished — значит, экран нужен уже сейчас.

## D-40. Подтверждение пака называет и позиции, и единицы

`Basic Pack added — 3 items, 6 units`.

**Основание.** §7.5 приводит пример «Basic Pack added — 6 items», а C-10 требует
не смешивать «уникальные позиции» и «единицы». Одна величина вместо двух в
операционной вводит в заблуждение: «6 items» при трёх строках выглядит как
ошибка списания. Обновление D-23: настройка `sound_on_scan_enabled` появилась
в `/settings`, потому что появился экран, который её читает.

## D-41. Карточка завершённой операции — полная (отменяет D-39)

`/operations/[id]` для Finished и Voided показывает всё, что перечисляет §12.2:
код, статус, временные отметки, категорию (если заполнена), позиции с
источником добавления, количеством, сохранённой стоимостью единицы и суммой
строки, плюс общий итог.

**Основание.** D-39 объявлял сокращённый экран заглушкой до реализации §12.
Заглушка снята. Ни одного обращения к текущей цене предмета на странице нет:
все суммы приходят из `unit_cost_snapshot_cents`, `line_total_cents` и
`total_cost_snapshot_cents` (§11.3, §18.16). Свойство проверяется тестом,
который меняет цену, имя и reference number уже после Finish и требует, чтобы ни
одна цифра карточки не сдвинулась.

Строка `individual` подписана «Individual scan», строка из пака — «From pack:
<название>»: §12.2 требует показывать источник, а §7.6/§7.7 запрещают их
смешивать (C-2).

## D-42. Сводка §12.3 агрегируется по предмету, а не по строке операции

`getOperationSummary()` объединяет позиции одного предмета: скан отдельно и он же
в составе пака дают одну строку сводки.

**Основание.** §12.3 — форма для РУЧНОГО переноса: в Symplast вносят «сколько
единиц предмета израсходовано», а не устройство операции. Две строки «Gauze 4x4»
в такой форме — приглашение ввести материал дважды. Источник добавления при этом
не теряется: он виден построчно в карточке §12.2 (D-41).

**Следствие.** Один предмет мог попасть в операцию по разной цене (D-5). Тогда
«стоимости единицы» у объединённой строки не существует, и поле опускается —
печатается только сумма строки. Средняя цена не выводится: она не равна ни
одному снимку и не воспроизводима при пересчёте.

## D-43. У аннулированной операции сводки нет — расхождение с Q-45

`getOperationSummary()` возвращает `undefined` для любого статуса, кроме
`Finished`; кнопки Print/Copy Summary на карточке Voided-операции нет.

**Основание.** Аналитик предлагал (Q-45) отдавать сводку и для Voided с пометкой
`VOIDED`. Решение принято в пользу отсутствия: §9.3 возвращает все списанные
количества на склад, то есть материалы НЕ израсходованы. Лист бумаги с пометкой,
которую можно не заметить, — это документ, по которому спишут материалы второй
раз. Состав аннулированной операции при этом остаётся виден Admin в карточке
(§12.2, D-38) — просто не в форме, предназначенной для переноса.

**Цена изменения.** Снять ограничение по статусу — одна строка; печать пометки —
ещё одна. Вопрос вынесен заказчику (Q-45).

## D-44. Текст Copy Summary собирается на сервере

`OperationSummaryView.text` приходит с сервера готовым; клиентская кнопка
(`copy-summary.tsx`) кладёт его в буфер как есть и ничего не форматирует.

**Основание.** D-18: себестоимость режется ОТСУТСТВИЕМ поля. Если бы текст
собирал клиент, суммы пришлось бы передать в клиентский бандл — и запрет
превратился бы в «не показываем на экране». Проверяемое свойство
`summary.text` не содержит `'$'` при выключенном `staff_can_see_cost` покрыто
тестом.

Колонки разделены табуляцией: так строки вставляются и в поле формы, и в
таблицу. Запасной путь копирования через `document.execCommand` оставлен,
потому что `navigator.clipboard` недоступен вне защищённого контекста, а молча
не скопировать — прямое нарушение §14.4.

## D-45. Одновременно существует не больше одной незакрытой инвентаризации

`startInventoryCountAction()` возвращает уже существующий черновик, а не создаёт
второй.

**Основание.** §5.10 требует, чтобы незавершённая инвентаризация сохранялась при
обновлении страницы, и говорит об инвентаризации в единственном числе. Если
разрешить второй черновик, первый станет невидимым: экран показывает последний,
а посчитанные позиции остались бы в потерянной записи. Это ровно тот класс
дефектов, который §18.24 запрещает для операций.

**Расхождение с операциями.** У операций несколько активных сосуществуют
намеренно (§8.5) — там это рабочий сценарий (несколько кабинетов). Сверка склада
такого сценария не имеет.

---

## D-46. Скан в режиме инвентаризации не создаёт строку

`scanForCountAction()` только находит предмет и отдаёт ожидаемое количество;
строка появляется после `recordCountLineAction()` с введённым числом.

**Основание.** §5.10 разделяет шаги 2 («сканирует предмет») и 3 («вводит
физически найденное количество»). Если создавать строку сразу на скане, в
инвентаризации появились бы позиции с непроверенным количеством, которые при
подтверждении списали бы остаток.

Пак в этом режиме отклоняется отдельным сообщением «… is a pack — scan the item
barcodes instead»: у пака нет собственного физического остатка (§18.10), считать
его нечего, а «Barcode not found» здесь было бы неправдой (§14.4).

Ожидаемое количество — снимок на момент ввода строки (поле `expected_quantity`),
а не текущий остаток: параллельно идущая операция иначе исказила бы уже
показанную пользователю разницу.

## D-47. Бэкап — `VACUUM INTO` с обязательной проверкой копии

`scripts/backup.ts` (`npm run db:backup`) делает копию механизмом SQLite и сразу
проверяет её `PRAGMA integrity_check` и пересчётом предметов, операций и
движений. Существующий файл не перезаписывается никогда.

**Основание.** §15 и NFR-16. База работает в режиме WAL (D-8 и `db/client.ts`),
поэтому часть подтверждённых транзакций в момент копирования находится в файле
`-wal`: `cp clinic.db backup.db` на работающей системе даёт копию без последних
операций либо повреждённую, и узнать об этом можно только при восстановлении.
`VACUUM INTO` пишет целостный файл из транзакции чтения.

Проверка копии — часть требования, а не украшение: непроверенный бэкап это
надежда. Процедура восстановления описана в README и прогнана: после подмены
файла `npm run db:migrate` печатает `Applied: nothing new`.

**Расписание не настраивается** — это решение по инфраструктуре клиники (Q-42,
NFR-16): периодичность, глубина хранения, место хранения и RPO/RTO не
утверждены. Скрипт рассчитан на внешний планировщик и на ручной запуск перед
обновлением. Копия рядом с рабочей базой защищает от ошибки оператора, но не от
отказа диска — это отмечено в README.

## D-48. Возврат фокуса в поле сканирования — без прокрутки страницы

`focusScanner()` вызывает `inputRef.current?.focus({ preventScroll: true })` и
дополнительно откладывает возврат фокуса, пока нажат указатель
(`pointerdown` → `pointerup`).

**Основание — дефект «Finish and Lock: тихий no-op».** Поле сканирования
удерживает фокус принудительно (D-34), и возврат фокуса запускается по `blur`
через `setTimeout(…, 0)`. Реальный клик человека длится 100–150 мс, то есть
таймер срабатывает МЕЖДУ `mousedown` и `mouseup`. Поле сканирования находится
вверху экрана, а кнопки — под списком позиций; когда список вырос, поле уже за
верхней границей окна, и `focus()` со скроллом по умолчанию возвращает его в
видимую область. Страница прыгает, кнопка уходит из-под курсора, и браузер не
выдаёт `click` вообще: нажатие пропадает молча.

Воспроизведено в Chrome (production build, Playwright, удержание кнопки 140 мс):
кнопка **Finish Operation** уезжала с `y=397` на `y=1154`, диалог не открывался,
операция оставалась `Active`. После исправления: `y=397 → y=397`, диалог
открывается, операция завершается. Дефект задевал не только Finish — так же
терялись нажатия Undo Last Scan, Manual Item Search, `−`/`+`, Remove и Void.

Фокус полю нужен (§7.5), прокрутка — нет: сканер печатает в поле независимо от
того, видно ли его. Отложенный возврат фокуса на время нажатия — вторая линия
защиты: между `mousedown` и `mouseup` страницу не трогает уже ничто.

**Цена изменения.** Если когда-нибудь понадобится подсвечивать поле скана
прокруткой, делать это придётся отдельным действием пользователя, а не
побочным эффектом фокуса.

## D-49. У «Finish and Lock» ровно два исхода, и оба видны

Кнопка защищена ref'ом от повторного входа (не только `disabled`), ошибка
показывается ВНУТРИ диалога и диалог при отказе остаётся открытым, успех
отмечается баннером до перехода, фокус при открытии переезжает на кнопку
подтверждения, `Escape` закрывает диалог.

**Основание.** §14.4 и §18: кнопка фиксирует деньги и количества, поэтому
«ничего не произошло» — недопустимый исход. Раньше при отказе сервера диалог
закрывался, а сообщение уходило в баннер наверху экрана, который в этот момент
почти всегда выше границы окна: пользователь видел ровно то же, что и при
пропавшем нажатии. `disabled` от двойного срабатывания не защищает — состояние
React применяется асинхронно, и два быстрых нажатия успевают пройти оба.

Серверная сторона того же требования покрыта тестом: повторный
`finishOperationAction` отвечает `Operation was already finished`, а не тихим
успехом; Finish аннулированной — `Operation was already voided`.

## D-50. Смена пароля — отдельный экран `/settings/password`, с текущим паролем Admin

`setAccountPassword()` существовал с первого спринта, но не был подключён ни к
одной странице: единственным способом сменить пароль был `npm run db:seed` с
паролем открытым текстом в `.env`. §3.3 и FR-12 (MVP) требуют обратного.

Решения экрана:

- **Отдельная страница, а не блок в `/settings`.** У действия другой ввод
  (текущий пароль, двойной ввод нового) и другой эффект (отзыв сессий), а форма
  настроек отправляется целиком — случайное сохранение настроек не должно
  тащить за собой смену пароля. Единственная ссылка — из `/settings`.
- **Спрашивается текущий пароль САМОГО Admin, а не пароль целевого аккаунта.**
  Это подтверждение личности: без него любой, кто подошёл к незалоченному
  планшету с открытой сессией Admin, менял бы пароли обоих аккаунтов клиники.
  Пароль цели для смены не нужен — §3.3 даёт Admin право менять оба.
- **После смены отзываются ВСЕ сессии затронутого аккаунта.** Иначе
  уволившийся сотрудник остаётся залогинен на своём устройстве, и смена пароля
  не даёт того, ради чего её делают (§15). Аккаунтов два и они общие (§2.3),
  поэтому «выкинуть всех» — это и есть ожидаемое поведение.
- **Свою сессию Admin не теряет.** Когда Admin меняет пароль себе, его сессии
  отзываются вместе с остальными, и обёртка тут же выпускает новую и ставит
  cookie: текущая вкладка продолжает работать, прочие устройства разлогинены,
  «повисшего» состояния нет.
- **Пароль нигде не задерживается.** Не логируется, не попадает в сообщения об
  ошибках, не пишется в аудит (там только факт смены и имя аккаунта), не
  возвращается в `FormState`, не остаётся в разметке — форма сбрасывается
  React после завершения действия.
- **Длина берётся из `MIN_PASSWORD_LENGTH`** (`src/auth/password.ts`), а не из
  числа в коде: в `setAccountPassword()` было зашито `10` в двух местах.

Три ошибки сформулированы отдельно (§14.4): «Current password is incorrect»,
«Passwords do not match», «Password must be at least 10 characters long».

Заодно закрыт тихий no-op в самом `setAccountPassword()`: несуществующий
`accountId` давал пустой `UPDATE` и запись в журнал «пароль изменён». Теперь это
ошибка.

**Не сделано намеренно.** Неверный текущий пароль на этом экране не увеличивает
счётчик блокировки входа (D-12): счётчик ведётся по паре (username, IP) для
страницы входа, и подбор пароля через уже авторизованную сессию Admin — другая
модель угрозы. Вопрос вынесен заказчику.

## D-51. Адрес размещения `/clinic` — константа сборки, а не переменная окружения

`src/base-path.ts` экспортирует `BASE_PATH = '/clinic'`; `next.config.ts`
импортирует её в `basePath`. Приложение доступно только по
`https://dazhyma.tech/clinic` — корень домена занят другим проектом.

**Почему не переменная окружения.** Next подставляет префикс в имена
статических файлов (`/clinic/_next/static/...`) на этапе сборки. Переменная,
которую можно поменять на запущенном контейнере, создавала бы впечатление
настраиваемости и давала бы белый экран при первой же попытке ею
воспользоваться. Смена адреса размещения = пересборка образа, и это записано
в `.env.example`.

**Где Next НЕ подставляет префикс сам** — проверено на собранном приложении в
браузере, каждый пункт исправлен:

- `NextResponse.redirect()` в `src/middleware.ts`: путь задаётся явным
  `url.basePath = BASE_PATH`. Без него неавторизованного пользователя уносило
  бы на `/login` в корень домена, то есть в чужой проект;
- атрибут `action` обычной GET-формы (`item-filters.tsx`,
  `inventory/receive/page.tsx`) — его отправляет браузер, а не Next;
- `src` у `next/image` с `unoptimized` (`item-photo.tsx`): в этом режиме
  лоадер возвращает путь как есть. `unoptimized` обязателен по D-19, поэтому
  плата за него — ручной префикс;
- обычный `<a href>` на route handler (`label-print.tsx`, скачивание этикетки).

`next/link`, `useRouter().push()` и `redirect()` из `next/navigation` префикс
получают сами — там `withBasePath()` дал бы `/clinic/clinic/...`; функция
идемпотентна, но полагаться на это не нужно.

**В БД префикс не хранится.** `items.photo_url` остаётся `/api/photos/<token>`:
адрес размещения — свойство развёртывания, а не данных, иначе переезд
приложения потребовал бы миграции. Свойство закреплено тестом
`tests/base-path.test.ts`.

**`matcher` middleware.** Пути в нём указываются без префикса — Next снимает
его до сопоставления. Отдельной строкой добавлен `'/'`: в шаблоне
`'/((?!…).*)'` группа с look-ahead является параметром пути, а параметр не
сопоставляется с пустой строкой, поэтому главная страница в matcher не
попадала и уходила без заголовка CSP. Обнаружено запросом `curl` к собранному
приложению, а не чтением кода.

## D-52. Cookie сессии ограничена префиксом (`path=/clinic`)

`sessionCookieOptions()` ставит `path: BASE_PATH`; `logoutAction` удаляет
cookie ТЕМ ЖЕ path.

**Основание.** На домене живут соседние приложения. С `path=/` токен сессии
клиники уходил бы в каждый их запрос — это утечка учётных данных за пределы
системы (§15) плюс риск конфликта имён cookie между проектами.

**Ловушка, которую это создаёт.** `cookies().delete(name)` без `path` гасит
cookie в корне домена и на `/clinic` не действует: logout стал бы фикцией —
кнопка нажата, сессия жива. Поэтому удаление выполняется объектом
`{ name, path }`. Проверено в браузере: после logout cookie в хранилище нет.

## D-53. CSP выдаётся middleware с одноразовым nonce, HSTS — статическим заголовком

`Strict-Transport-Security: max-age=31536000; includeSubDomains` объявлен в
`next.config.ts`. `Content-Security-Policy` собирается в `src/middleware.ts` на
каждый запрос с новым nonce, ставится и на запрос (его читает рендерер Next и
помечает свои инлайновые скрипты), и на ответ.

**Почему nonce, а не `script-src 'unsafe-inline'`.** Next вставляет инлайновые
скрипты гидрации, и разрешить инлайн целиком — значит выключить ту часть
политики, ради которой её добавляют. Nonce + `strict-dynamic` разрешает ровно
скрипты Next и загружаемые ими чанки.

**`style-src 'unsafe-inline'` оставлен и это не выбор.** Геометрия этикетки
(миллиметры выбранного пресета) и размер миниатюры задаются атрибутом `style`,
а на атрибуты стиля nonce не распространяется в принципе.

Страница входа ВКЛЮЧЕНА в matcher (раньше исключалась): иначе единственная
доступная без сессии страница осталась бы без политики. Редирект для неё
отключён проверкой пути, а не отсутствием в matcher. Файл `icon.svg` исключён
вместе со статикой — он нужен на странице входа, где сессии ещё нет.

**Проверено в браузере** (Chromium, production build, обход разделов
Inventory → Barcode → Operations → Count → Settings → logout): ошибок и
предупреждений в консоли ноль, гидрация работает, инлайновый SVG штрихкода
отображается, звук скана и оптимистичный отклик не задеты.

`includeSubDomains` действует на весь домен, а не только на `/clinic`, —
решение владельца домена, вынесено заказчику. `preload` не выставлен: это
необратимое на практике обязательство.

## D-54. Образ — обычная сборка с полным `node_modules`, без `output: 'standalone'`

`Dockerfile`: `node:24-bookworm-slim`, четыре стадии (deps → builder →
prod-deps → runner), запуск от пользователя `node`, порт 3000, том `/app/data`.

**Почему bookworm, а не alpine.** Нативный код в трёх зависимостях:
`better-sqlite3` и `@node-rs/argon2` — `.node`-биндинги, `sharp` — libvips.
Готовые сборки публикуются под glibc; под musl часть пришлось бы собирать из
исходников. Экономия ~80 МБ не стоит риска молча получить неработающее
хеширование паролей.

**Почему не `standalone`.** Трассировщик Next копирует `.node`-файлы не всегда
предсказуемо, а место на сервере есть. Надёжность выше размера.

**`tsx` и `typescript` переведены в `dependencies`.** Не небрежность: `tsx`
исполняет `scripts/migrate.ts` в entrypoint, а `typescript` требуется самому
Next, чтобы прочитать `next.config.ts` (в нём `basePath`) при `next start`.
Проверено: без пакета `typescript` `next start` пытается доставить его через
`npm install` на лету — в контейнере без сети и без прав root это отказ старта.

**Миграции — в entrypoint до сервера, сид — отдельной командой.** Приложение,
которое пишет остатки и деньги в схему, отличающуюся от ожидаемой, хуже
недоступного приложения (§16). Сид пересоздаёт два общих аккаунта клиники
(§2.3) и на каждом рестарте выполняться не должен.

**Healthcheck** — `fetch` из Node по `/clinic/login`: в slim-образе нет ни
curl, ни wget, а страница входа единственная не требует сессии и не отдаёт
данных инвентаря.

**Не проверено сборкой.** На машине разработки Docker отсутствует
(`docker: command not found`), образ собран не был.

## D-56. Распознавание штрихкода отделено от подтверждённой мутации

Дополнение к ТЗ отменяет прежнее решение C-9/D-31 об автоматическом добавлении
сразу после скана. Камера и HID-сканер теперь используют один двухэтапный
сценарий:

1. read-only `resolveBarcodeForConfirmation()` находит объект и возвращает
   данные карточки;
2. только кнопка **Add** создаёт `clientEventId` и вызывает существующую
   `scanIntoOperationAction()`.

У read-only действия нет `operationId`, количества или ключа идемпотентности,
поэтому распознавание технически не способно создать движение. Обновление
страницы, **Scan Again**, **Cancel** и закрытие камеры только удаляют локальное
состояние карточки.

Камера реализована через `getUserMedia` с `facingMode: environment` и
`@zxing/browser`/`@zxing/library`, ограниченные форматом Code 128. Это даёт один
путь для Safari iOS/iPadOS и Chrome Android. Кадры декодируются из центральной
области, совпадающей с заметной направляющей рамкой. Пока карточка открыта,
decode loop приостановлен; поток камеры остаётся открытым, поэтому после
успешного **Add** не требуется повторное разрешение и можно сразу сканировать
следующий предмет.

В Inventory Count подтверждение открывает поле фактического количества, но не
создаёт движение. В Receive Stock подтверждение открывает форму поставки;
движение появляется только после сохранения формы, после чего пользователь
возвращается к сканеру.

## D-57. Текущее значение штрихкода предмета берётся из SKU (отменено D-65)

Дополнение заказчика изменяет прежнее правило §5.5/§18.7: если у предмета
заполнен SKU, Code 128 кодирует нормализованный SKU; если SKU пуст, используется
автоматический постоянный `internal_code` вида `ITM-NNNNNN`.

Изменение SKU через Edit синхронизирует `items.barcode_value`. Старое значение
из `barcode_registry` не удаляется и остаётся алиасом того же предмета. Поэтому
ранее распечатанная этикетка продолжает находить товар, а один и тот же код
по-прежнему нельзя присвоить разным предметам или паку. Для нескольких алиасов
у одного владельца уникальный индекс `(owner_type, owner_id)` заменён обычным;
глобальная уникальность продолжает обеспечиваться первичным ключом
`barcode_registry.barcode_value`.

## D-58. Inventory Count — один общий черновик с неизменяемым историческим отчётом

Новая навигация разделяет Inventory на Receive Stock, Inventory Count и
Items & Packs. Одновременно существует не более одного общего черновика
инвентаризации: это обеспечивают и повторное открытие существующего черновика
в action-слое, и частичный уникальный индекс БД. Staff и Admin могут продолжать,
завершать и отменять один и тот же черновик.

Каждая сохранённая строка содержит снимки названия, кодов, фотографии и единицы,
а также роль аккаунта, последним изменившего Actual. Завершение повторно читает
актуальный складской остаток и создаёт движение на величину
`Actual - current_quantity`, поэтому даже при параллельной поставке или операции
итоговый остаток становится ровно равен введённому Actual. Завершённые отчёты
читаются только из снимков и не меняются после редактирования карточки товара.

## D-59. Item History объединяет журнал движений и структурированные изменения

Количественная история не дублируется: она читается из неизменяемого
`inventory_movements`, включая поставки, инвентаризации, операции, возвраты,
Void и ручные корректировки. Для изменений карточки добавлен отдельный
append-only `item_history_events` со старым/новым значением и ролью аккаунта.

Item History доступна только Admin, причём проверка выполняется в action-слое,
а не только скрытием ссылки. Фотографии, использованные в завершённых
инвентаризациях, не удаляются при последующей замене фотографии товара, иначе
исторический снимок перестал бы отображаться.

Receive Stock остаётся самостоятельным движением без сущности «поставка»:
заказчик подтвердил, что отдельный документ поставки и его номер не требуются.

## D-60. Удаление завершённой инвентаризации — мягкое и через обратные движения

Завершённый Inventory Count не удаляется физически: `deleted_at` скрывает его
из Inventory History и отчётов, но сохраняет FK из неизменяемого журнала.
Каждое исходное `count_correction` получает точное обратное движение с
детерминированным ключом `count-delete:{countId}:movement:{movementId}`.

Маркер удаления, обратные движения и audit-запись создаются одной
`BEGIN IMMEDIATE` транзакцией. Поэтому более поздние поставки/операции остаются
на месте, частичный возврат невозможен, а повторный запрос не меняет остатки.
Отрицательный итог допустим: блокирование сделало бы возврат неточным.

## D-61. Delete Item различает физическое удаление и необратимый архив

Неиспользованный Item с нулевым остатком удаляется физически вместе с
`barcode_registry`, `item_history_events` и загруженной фотографией. Автоматические
события `Item Created` и audit сами по себе этому не препятствуют.

Если есть движение, операция, строка Inventory Count, существующий Pack или
ненулевой остаток, Item получает `archived_at` и `status = inactive`. Архив
необратим: его нельзя редактировать, сканировать, принимать, считать или
добавлять в Pack. Остаток и вся историческая информация сохраняются.

## D-62. Delete Pack сохраняет использованные наборы

Pack, который ни разу не добавлялся в операцию, удаляется вместе с составом,
barcode alias и фотографией; входящие Item не затрагиваются. Факт использования
проверяется и по текущим `operation_items`, и по append-only событию
`pack_added`, поэтому последующее удаление строки операции не превращает
использованный Pack в «неиспользованный».

Использованный Pack архивируется необратимо через `archived_at` и
`status = inactive`; прошлые строки операций и остатки Item не меняются.

## D-63. Переходы и preview этикетки не влияют на учёт и печать

Короткая анимация входа страницы и модальных окон реализована только CSS и
отключается через `prefers-reduced-motion`; scan loop и server actions она не
оборачивает. Крупный Label Preview — отдельный экранный блок. Печатный
`.label-sheet` остаётся в миллиметрах и показывается только в `@media print`,
поэтому увеличение preview не меняет SVG, PNG или физический размер печати.

## D-64. Массовая печать не создаёт серверных черновиков и повторно валидируется

Выбор Bulk Labels хранится в `sessionStorage`: поиск, фильтры, переход на Preview
и возврат не сбрасывают выбранные Item и индивидуальные Copies, но в БД не
появляется новая учётная сущность. Страница доступна обеим аутентифицированным
ролям, как существующий View Barcode.

Клиентское состояние не считается доверенным. Preview и PDF получают только
массив `{ itemId, copies }` и `sizeId`; сервер повторно проверяет сессию,
уникальность ID, `status = active`, отсутствие `archived_at`, допустимый размер,
1–100 копий на Item и максимум 10 000 лейблов. Тело запроса ограничено 512 KiB
в том числе для chunked-запроса.

PDF формируется сервером через PDFKit и SVG-to-PDFKit: US Letter Portrait,
поля 6 mm, промежуток 2 mm, Code 128 и текст остаются векторными. Сетка Preview
использует те же константы миллиметров, поэтому количество строк/колонок и
перенос страниц совпадают с PDF.

## D-65. Item Code — единственный идентификатор и barcode value

Новое дополнение к ТЗ отменяет D-57. Пользовательского поля SKU больше нет ни
в формах и ответах сервера, ни в текущих или исторических таблицах. Для Item
графический Code 128, читаемый текст и технический `barcode_value` всегда равны
постоянному `internal_code` формата `ITM-######`; для Pack действует то же
правило с `PCK-######`.

Миграция сохраняет существующие системные коды, возвращает каждому Item его
`internal_code` как `barcode_value`, удаляет прежние пользовательские barcode
aliases и физически удаляет `sku`, `sku_snapshot` и соответствующий индекс.
Старые распечатанные пользовательские коды после миграции намеренно не
разрешаются. Устаревшее поле `sku` во входном объекте игнорируется, поскольку
его нет в whitelist валидируемых полей и оно не может попасть в домен или БД.

Полный SVG-лейбл является общей основой Preview, Print, Download SVG, Download
PNG и Bulk PDF. Он содержит название, Reference Number при наличии,
графический barcode и тот же читаемый системный код. PNG растеризуется из этого
SVG, а не генерирует альтернативный штрихкод.

## D-66. Визуальная система централизована и не влияет на печать

Палитра Silver Strand / Tricorn Black / Egret White / Snowbound / Cultured
Pearl / Portsmouth / Minimalist / Eventide сведена к CSS-токенам в
`globals.css`. Общие кнопки, поля, карточки, статусы, уведомления, пустые и
загрузочные состояния находятся в `src/app/_components`; старые Tailwind-цвета
также переназначены централизованно, чтобы редкое состояние не возвращало
предыдущую холодную тему.

Базовый размер шрифта остаётся 17 px: это осознанно сохраняет крупный текст для
сенсорных экранов клиники. Успешные и информационные уведомления исчезают через
пять секунд, а ошибки и предупреждения остаются возле действия. Переход страницы
использует только opacity без геометрического сдвига и без containing block,
мешающего fixed-интерфейсу камеры; motion отключается через
`prefers-reduced-motion`.

Экранные поверхности стали тёплыми, но `.label`, Bulk PDF/SVG/PNG и print CSS
принудительно остаются чёрно-белыми. Поэтому визуальная тема не меняет размеры,
quiet zone, контраст или сканируемость штрихкода.

## D-67. Поиск и сканирование используют единое явное подтверждение

Текстовый поиск, клавиатурный HID-сканер и камера сведены в один селектор.
Пустое поле не загружает каталог; результаты ранжируются по точному совпадению,
префиксу кода/reference, префиксу названия и остальным вхождениям. В Operations
поиск включает активные Item и Pack, а Receive Stock и Inventory Count — только
Item. Ответ поиска read-only и не содержит себестоимость.

Выбор результата всегда открывает ту же карточку, что и сканирование. До Add или
Confirm Item нет движения остатка или иной мутации. Для ручного результата
вторичная кнопка возвращает к сохранённому поиску; для сканера — запускает новый
скан.

Камера рендерится portal-ом непосредственно в `body`, блокирует прокрутку
страницы и делает `#app-root` inert на время работы. Поток и все его tracks
закрываются при выходе; переключение камеры и фонарь показываются только при
наличии соответствующих возможностей устройства. Safe-area и `100dvh`
сохраняют доступность управления в Safari iOS/iPadOS и Chrome Android.

## D-68. Коды ищутся без учёта оформления, но хранятся без изменений

Нормализация применяется только во время сравнения: Unicode приводится к NFKC,
все символы кроме букв и цифр удаляются, буквы приводятся к верхнему регистру.
Исходный поиск остаётся первым условием, поэтому названия и буквальные значения
работают как раньше; нормализованное условие добавляется для названия (в нём
заказчик хранит NDC и иные обозначения), Item Code, Reference Number и barcode
value Item/Pack. Строка не преобразуется в число,
начальные нули сохраняются, NDC 10/11 не конвертируется.

SQLite-соединение регистрирует детерминированную `normalize_code()`, чтобы
каталог до 5000 Item фильтровался в БД, а не загружался целиком в JavaScript.
Отдельного поля NDC нет: заказчик подтвердил, что NDC и иные обозначения могут
быть частью существующего названия или Reference Number.

## D-69. Voided operation может быть удалена Admin вместе с историей

Окончательное удаление разрешено только Admin и только для статуса `Voided`;
проверка повторяется в action и domain слоях. Удаляются `operation_items`,
`operation_events`, связанные `inventory_movements` и сама операция, после чего
пишется `operation.deleted` в audit log. Счётчик case code не откатывается и код
не переиспользуется.

Удаление не вызывает `applyMovement` и не меняет `items.current_quantity`:
возврат уже выполнен во время Void. Перед стиранием домен проверяет, что сумма
движений операции равна нулю отдельно для каждого Item; несбалансированная
история блокирует удаление, иначе исчез бы источник складского инварианта.

## D-70. Фильтры Past Operations используют общую UI-систему

Search, Status, Doctor и обе даты собраны в одну адаптивную панель на общих
`Input`, `Select`, `FieldLabel` и `Button`. На широком экране поля образуют
12-колоночную компактную сетку, на iPad и телефонах переходят в две или одну
колонку. `Apply Filters` использует primary-вариант, а `Clear Filters` —
secondary-ссылку на чистый `/operations`, поэтому очистка сразу возвращает
полную историю без отдельного клиентского состояния.

## D-71. Существующие dropdown используют единый доступный listbox

Все существующие нативные `select` переведены на общий `Select`: визуальный
trigger и открытый listbox одинаковы в Safari, Chrome, iPadOS и Android, а
скрытый нативный `select` сохраняет `name`, текущее значение, Server Actions,
GET-фильтры и сброс формы. Меню рендерится через portal поверх карточек,
ограничивается viewport и при нехватке места открывается вверх; доступны
стрелки, Home/End, Enter, Escape, typeahead и touchscreen.

По уточнению заказчика новые dropdown не создаются: существующие текстовые поля
с `datalist` для category, unit и storage location остаются текстовыми полями.
Строка действий фильтров вынесена в общий `FilterActions`; primary Apply и
secondary Clear используют уже существующую общую систему кнопок.

## D-72. Patient ID — единственное разрешённое поле пациента и хранится зашифрованным

Новое ТЗ и прямое подтверждение заказчика отменяют прежний запрет §2.4/§18.3
только в отношении `Patient ID`. Имя, дата рождения, телефон, описание surgery
и любые другие данные пациента по-прежнему запрещены. Значение состоит из 1–64
цифр, обязательно для новых surgeries, не редактируется и остаётся `NULL` у
старых записей.

В SQLite нет plaintext-столбца: `patient_id_encrypted` содержит AES-256-GCM с
новым nonce для каждой записи, а `patient_id_lookup` — keyed HMAC для точного
индексированного поиска. Ключ `PATIENT_ID_SECRET` хранится только в env. Patient
ID не включается в audit summary, Symplast summary, URL, browser history,
cookies или localStorage. Обычный список прошлых surgeries не получает поле с
сервера; расшифровка выполняется только после авторизации для активной/полной
карточки и результатов POST-поиска.

## D-73. Surgery — только пользовательская терминология

Во всех видимых текстах `Operation/Operations` заменены на `Surgery/Surgeries`.
Технические маршруты `/operations`, таблицы, внешние ключи, event types,
movement types, TypeScript-модели и функции не переименовываются: это не несёт
пользы пользователю, но создало бы риск для существующих данных и учётного ядра.
