# Часть 1. Жизненный цикл операции

## 1.1. Диаграмма

```
                    Start New Operation
                    (Staff | Admin)
                            │
                            ▼
                     ┌─────────────┐
      Finish Operation│             │  Void Operation
      + Finish and Lock│   ACTIVE   │  (только Admin)
      (Staff | Admin)  │             │───────────────┐
              ┌────────│             │               │
              │        └─────────────┘               │
              │              ▲                       │
              │              │ Resume                │
              │              │ (не меняет статус)    │
              ▼                                      ▼
       ┌─────────────┐   Void Operation      ┌─────────────┐
       │  FINISHED   │──────────────────────▶│   VOIDED    │
       │             │   (только Admin)      │             │
       └─────────────┘                       └─────────────┘
                                                    │
                                              ✗ терминальное
                                                состояние
```

## 1.2. Таблица переходов

| # | Из | В | Действие | Инициатор | Условия | Побочные эффекты | ТЗ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| T1 | — | **Active** | Start New Operation | Staff, Admin | — | Генерируется уникальный случайный `random_case_code`; `created_at` = now; при необходимости выбирается `procedure_category`; запись **немедленно сохраняется** на сервере ещё до первого скана; открывается экран сканирования | §7.3, §8.1 |
| T2 | Active | **Finished** | Finish Operation → диалог → **Finish and Lock** | Staff, Admin | Явное двухшаговое подтверждение пользователем | `finished_at` = now; `total_cost_snapshot` = Σ `line_total`; список позиций, количества и стоимости блокируются; операция уходит из блока активных в историю. **Движений остатков не создаётся** — они уже созданы при добавлении позиций | §9.2, §11.5, §18.14 |
| T3 | Active | **Voided** | Void Operation → диалог → **Void Operation** | **только Admin** | Операция не в статусе Voided | `voided_at` = now; `void_reason` (необязательно); создаются движения `void_reversal` на чистое списание по каждому предмету; операция исключается из финансовых итогов и из блока активных | §9.3, §10.3, §18.19 |
| T4 | Finished | **Voided** | Void Operation → диалог → **Void Operation** | **только Admin** | Операция не в статусе Voided | То же, что T3. Зафиксированный `total_cost_snapshot` **сохраняется в записи**, но исключается из агрегированных финансовых итогов | §9.3, §21.5 |
| T5 | Active | Active | Resume Operation | Staff, Admin | Есть операция в статусе Active | Статус **не меняется**. Восстанавливаются список позиций, количества, зафиксированные цены, текущий итог; сканер готов | §8.3 |

## 1.3. Запрещённые переходы и запрещённое поведение

| Запрет | Что именно недопустимо | Ожидаемое поведение системы | ТЗ |
| --- | --- | --- | --- |
| **Автозавершение по таймеру** | Никакой планировщик, cron, таймаут сессии или фоновая задача не переводит Active → Finished или Active → Voided | Операция остаётся Active неограниченно долго. В коде отсутствует любой путь смены статуса без явного пользовательского действия | §9.1, §16, §18.13 |
| **Завершение по сессии** | Logout, истечение сессии, закрытие браузера, закрытие вкладки, перезапуск устройства, перезапуск сервера, потеря интернета — не меняют статус | Статус до = Active, статус после = Active; состав и количества идентичны; движений остатков не создано | §3.4, §8.2, §16 |
| **Повторный Void** | Voided → Voided | Запрос отклоняется; сообщение **Operation was already voided**; **новых движений `void_reversal` не создаётся**; остаток не меняется. Гарантия — детерминированный `idempotency_key` вида `void:{operation_id}:item:{item_id}` с уникальным ограничением БД | §9.3, §16, §18.21 |
| **Двойной возврат остатков** | Два параллельных запроса Void (двойной клик, ретрай после таймаута) | Ровно один набор движений `void_reversal`; второй запрос перехватывается нарушением уникальности и возвращает результат первого как успешный | §9.3, §10.4, §16 |
| **Перезапись активной операции** | Создание новой операции не изменяет и не заменяет существующую активную | При наличии активных показывается их список с **Resume** у каждой и кнопкой **Start Another Operation**; несколько Active сосуществуют | §8.5, §16, §18.24 |
| **Изменение завершённой операции** | Добавление/удаление позиций, изменение количества, изменение снимков стоимости в статусах Finished и Voided | Отклоняется на сервере, независимо от состояния UI | §9.2, §11.3, §16 |
| **Пересчёт истории** | Изменение `Item.name`, `sku`, `reference_number`, `current_unit_cost`, состава пака или количеств в паке не порождает UPDATE строк завершённых операций | Завершённая операция показывает те же значения, что и до изменения | §11.3, §18.16, §18.17 |
| **Физическое удаление** | Удаление записи операции из базы через обычный интерфейс | Действия «удалить операцию» в UI нет; вместо него — Void | §9.3 |
| **Возврат «старого общего остатка»** | При Void нельзя записать в остаток предмета то значение, которое было до операции | Создаются обратные движения ровно на списанное количество; поступления, сделанные после операции, сохраняются | §10.3, §18.20 |
| **Voided → любое состояние** | Разворот Void, повторное завершение, реактивация | Отклоняется; Voided — терминальное состояние | §9.3 |
| **Finished → Active** | «Переоткрытие» завершённой операции | ТЗ такого перехода не предусматривает → запрещено. Единственный выход из Finished — Void ⚠ см. `open-questions.md` | §9.2, §9.3 |

## 1.5. Инвариант «операция не привязана к сессии»

Прямое следствие §3.4 и §8.2 в сочетании с §2.3 (два общих аккаунта):

- Активная операция принадлежит **системе**, а не сессии, устройству или вкладке.
- Операция, начатая на планшете, возобновляема на компьютере — состояние живёт на сервере (§8.1: «Нельзя хранить всю операцию только в памяти страницы»).
- Никакая логика вида «очистить активные операции пользователя при выходе» не допускается.

# Часть 2. Движения остатков (§10.4)

Единственный способ изменить `Item.current_quantity` — создать движение. Прямая запись остатка мимо журнала движений запрещена: именно журнал предотвращает неправильный пересчёт при изменениях, совершённых после операции (§10.4).

## 2.1. Типы движений

| Тип | Знак `quantity_delta` | Что делает с количеством | Триггер | Инициатор | `operation_id` | `reason` | ТЗ |
| --- | :---: | --- | --- | --- | :---: | --- | --- |
| `received` | **+** | Увеличивает остаток на количество поступивших единиц | Подтверждение **Receive Stock** | Staff, Admin | NULL | опционально | §5.8, §10.4 |
| `used_in_operation` | **−** | Уменьшает остаток на использованное количество | Скан предмета, скан пака (по строке на предмет), ручное добавление, нажатие `+` в активной операции | Staff, Admin | **обязателен** | — | §7.5, §7.7, §10.1 |
| `returned_from_operation` | **+** | Возвращает на склад количество, снятое ранее этой же активной операцией | Нажатие `−`, удаление строки, **Undo Last Scan** в активной операции | Staff, Admin | **обязателен** | — | §7.9, §10.2, §18.18 |
| `manual_adjustment` | **±** | Увеличивает или уменьшает остаток на указанную величину | Ручная корректировка Admin | **только Admin** | NULL | **обязателен** (damaged / expired / missing / inventory correction / received outside normal process / other) | §5.9, §10.4 |
| `inventory_count_correction` | **±** | Приводит остаток к фактически посчитанному: `delta = counted − expected` | Применение общей инвентаризации | Staff, Admin | NULL | ссылка на инвентаризацию | §5.10, §10.4 |
| `void_reversal` | **+** | Возвращает **ровно то чистое количество, которое списала конкретная операция** | Void Operation | **только Admin** | **обязателен** | `void_reason` операции | §9.3, §10.3, §10.4 |

## 2.2. Начальное количество предмета

§5.4 требует обязательное поле `Initial Quantity` (допускается 0), но §10.4 не называет тип движения для него.

**ДОПУЩЕНИЕ:** при создании предмета с `Initial Quantity = K > 0` создаётся движение `received` с `quantity_delta = +K`, `reason = "initial stock"`, `idempotency_key = init:{item_id}`. При `K = 0` движение не создаётся. Это сохраняет инвариант `current_quantity == Σ quantity_delta` без введения седьмого типа движения. См. `open-questions.md`.

## 2.3. Что НЕ порождает движений

| Действие | Почему движения нет | ТЗ |
| --- | --- | --- |
| Изменение состава пака (`PackItem`) | Пак — цифровое сокращение; изменение состава действует только на будущие сканирования | §6.5, §6.7, §18.17 |
| Изменение стоимости предмета | Стоимость и количество — независимые величины | §5.7, §11.3 |
| Переход Active → Finished | Все списания уже сделаны в момент добавления позиций | §9.2, §10.1 |
| Создание/редактирование пака | Пак не имеет собственного остатка | §6.5, §18.10 |
| Редактирование атрибутов предмета (название, SKU, фото, категория, место, порог, заметки, статус) | Не влияет на количество | §5.7 |
| Просмотр, печать этикеток, сводка | Только чтение | §5.6, §12.3 |

## 2.4. Ключевая формула Void

При Void операции `O` для каждого предмета `i`, фигурировавшего в `O`:

```
чистое_списание(O, i) = |Σ quantity_delta| где movement_type = used_in_operation
                        − Σ quantity_delta  где movement_type = returned_from_operation

void_reversal(O, i).quantity_delta = + чистое_списание(O, i)
```

Иными словами: возвращается **ровно то, что операция реально забрала**, с учётом всех промежуточных возвратов. Не «остаток до операции», не «сумма всех used».

**Пример с промежуточным возвратом.**

| Шаг | Действие | Движение | Остаток |
| --- | --- | --- | ---: |
| 1 | Остаток на складе | — | 20 |
| 2 | Операция O: скан ×5 | `used_in_operation` −5 | 15 |
| 3 | В операции количество уменьшено с 5 до 2 | `returned_from_operation` +3 | 18 |
| 4 | Finish | — | 18 |
| 5 | Void O | `void_reversal` **+2** (не +5) | **20** |

## 2.5. Канонический пример из §10.3

| Шаг | Действие | Тип движения | `quantity_delta` | Остаток после |
| --- | --- | --- | ---: | ---: |
| 1 | Исходный остаток gauze | — | — | **10** |
| 2 | Операция использовала 2 | `used_in_operation` | −2 | **8** |
| 3 | Поступила поставка 20 | `received` | +20 | **28** |
| 4 | Admin аннулировал операцию | `void_reversal` | **+2** | **30** |

Неверные варианты, которые система обязана исключать:
- **10** — восстановление «старого общего остатка» (стирает поставку) — прямо запрещено §10.3 и §18.20;
- **12** — восстановление «остатка до операции плюс что-то» — та же ошибка;
- **32** — двойное применение возврата — запрещено §9.3 и §16.

## 2.6. Инварианты движений

| # | Инвариант | Как проверяется |
| --- | --- | --- |
| I-1 | `Item.current_quantity == Σ InventoryMovement.quantity_delta WHERE item_id = X` | Регламентная сверка; расхождение — критический дефект |
| I-2 | Запись движения и обновление `current_quantity` — одна транзакция | Ревизия кода; тест на прерывание между операциями |
| I-3 | `quantity_delta ≠ 0` | Check-констрейнт |
| I-4 | `used_in_operation`, `returned_from_operation`, `void_reversal` ⇒ `operation_id IS NOT NULL` | Check-констрейнт |
| I-5 | `manual_adjustment` ⇒ `reason IS NOT NULL` | Check-констрейнт (§5.9) |
| I-6 | Для одной операции существует **не более одного** набора `void_reversal` | `UNIQUE (idempotency_key)` при детерминированном ключе `void:{operation_id}:item:{item_id}` |
| I-7 | После перехода операции в Finished по ней не создаются движения `used_in_operation` / `returned_from_operation` | Проверка статуса в бизнес-логике |
| I-8 | После перехода операции в Voided по ней не создаются никакие движения | Проверка статуса + I-6 |
| I-9 | Сканирование пака порождает движения по всем позициям либо ни по одной | Одна транзакция на весь пак (§16) |
| I-10 | Повторная отправка одного scan event порождает 0 новых движений | `UNIQUE (idempotency_key)`; повторный запрос возвращает результат первого как успешный |

## 2.7. Обработка повторных запросов (идемпотентность)

Три сценария, которые ТЗ обязывает выдержать (§10.4, §16, §8.4):

| Сценарий | Что происходит | Ожидаемый результат |
| --- | --- | --- |
| Двойное срабатывание сканера / двойной клик по `+` | Клиент отправляет два запроса с **одинаковым** `client_event_id` | Второй запрос натыкается на нарушение `UNIQUE (idempotency_key)`, обработчик возвращает состояние после первого запроса с кодом успеха. Пользователь видит одно добавление, не ошибку |
| Ретрай после сетевого таймаута | Первый запрос дошёл и применился, ответ потерян; клиент повторяет с тем же ключом | Одно движение, корректный ответ. Данные не задваиваются |
| Синхронизация очереди после offline | Очередь отправляется повторно целиком | Применяются только те события, ключей которых ещё нет |

**Критично:** ключ генерируется **клиентом в момент события** и не меняется при ретраях. Ключ, сгенерированный сервером при получении запроса, идемпотентности не даёт.

# Часть 3. Вспомогательные жизненные циклы

## 3.1. Инвентаризация (§5.10) — ⚠ статусы ТЗ не заданы

ТЗ описывает процесс, но не даёт статусной модели. **ДОПУЩЕНИЕ:**

```
Draft ──── подтверждение всех строк ────▶ Applied  (терминальное)
  │
  └──────── отмена ────────▶ Cancelled  (терминальное)
```

| Состояние | Смысл | Побочные эффекты перехода |
| --- | --- | --- |
| `Draft` | Инвентаризация начата, строки вводятся. **Переживает обновление страницы** (§5.10 — обязательное требование) | — |
| `Applied` | Подтверждена; остатки скорректированы | Для каждой строки с `difference ≠ 0` создаётся движение `inventory_count_correction` |
| `Cancelled` | Отменена | Движений не создаётся, остатки не меняются |

Строка инвентаризации хранит `expected_quantity` как **снимок** на момент ввода — иначе при параллельной работе операционного экрана разница посчитается неверно.

## 3.2. Статус предмета и пака (§5.7, §6.2)

```
active ⇄ inactive
```

Переключается Admin. ⚠ ТЗ не описывает поведение при сканировании неактивного объекта, но §14.4 приводит эталонное сообщение **Item is inactive** — из чего следует, что сканирование неактивного предмета отклоняется. То же поведение для пака и для предмета внутри активного пака — открытый вопрос.

## 3.3. Сессия пользователя

```
Не авторизован ──login──▶ Авторизован ──logout / истечение──▶ Не авторизован
```

**Ключевое правило:** ни один переход сессии не влияет на статус операции (§3.4, §8.2). После повторного входа система предлагает возобновить активную операцию (§3.4, §8.3).

## 3.4. Состояние синхронизации клиента (§8.4)

```
Synced ──потеря связи──▶ Offline (N changes waiting) ──восстановление──▶ Syncing ──▶ Synced
```

| Состояние | Что видит пользователь | Объём |
| --- | --- | --- |
| `Synced` | Индикатор сохранения без предупреждений | MVP |
| `Offline` | **Changes are not synced — check connection**; в полной версии — `Offline — 3 changes waiting to sync` | MVP: предупреждение обязательно. Локальная очередь и счётчик — V2 (§20) |
| `Syncing` | Отправка накопленных событий; каждое со своим неизменным `idempotency_key` | V2 |

Минимум для MVP (§8.4, последний абзац): система не теряет уже подтверждённые сервером данные и ясно предупреждает, что новые сканирования не синхронизированы.
