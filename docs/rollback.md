# Откат обновления

Документ отвечает на один вопрос: что делать, если обновление выкачено и его
нужно отменить.

Короткий ответ: **код откатывается свободно, схема БД — нет.** Раннер миграций
(`src/db/migrate.ts`) применяет `drizzle/*.sql` только вперёд; down-миграций в
проекте нет и не планируется. При этом `docker-entrypoint.sh` применяет
миграции **автоматически при старте контейнера**, до запуска сервера, — то есть
деплой и миграция происходят одним действием, отдельного решения на этот счёт
никто не принимает.

Отсюда правило: **снимать резервную копию до деплоя, а не после.**

---

## 1. Что откатывается само, а что нет

| Слой | Откатывается | Чем |
|---|---|---|
| Код приложения | да | `git revert` или деплой предыдущего образа |
| Данные | да, с потерями | восстановление из копии `npm run db:backup` |
| Схема БД | нет | down-миграций нет; правится отдельной миграцией вперёд |

---

## 2. Совместимость миграций со старым кодом

Не все миграции одинаково опасны при откате кода. Разница принципиальная.

**Совместимые — старый код с ними работает без изменений.** Это те, что только
добавляют таблицы, колонки и обычные индексы: старый код их не читает и не
пишет, а `NULL` в новых колонках его устраивает.

- `0006_doctors_and_case_codes.sql` — совместима. Таблица `doctors` и колонки
  `doctor_id`, `case_code`, `case_number`, снимки врача старому коду не видны.
  `UNIQUE` на `case_code` не мешает: SQLite допускает произвольное число `NULL`
  в уникальном индексе, а старый код пишет туда именно `NULL`.

**Несовместимые — навязывают старому коду правило, которого он не знает.** Это
триггеры и частичные уникальные индексы: они срабатывают независимо от того,
какой код обращается к базе.

- `0007_active_operation_limits.sql` — **несовместима**. Триггер предела
  операционных кабинетов отклонит третью активную операцию, даже если её создаёт
  старый код, для которого §8.5 не ограничивает их число. Пользователь увидит
  «The change was not saved» — обработчика этой ошибки в старом коде нет.

Проверено на живой схеме: две вставки в стиле старого кода (без `doctor_id` и
`case_code`) проходят, третья отклоняется с `both operating rooms are already in
use`.

Практический вывод: **откатывать один только код недостаточно.** Нужно снять
ещё и ограничения — шаг 3 ниже.

---

## 3. Порядок отката

### Шаг 1. Остановить приложение

```bash
docker compose -f docker-compose.prod.yml stop clinic-app
```

Пока сервер пишет в базу, менять схему и подменять файл нельзя.

### Шаг 2. Откатить код

`git revert` нужных коммитов либо деплой предыдущего образа. Пересобирать
контейнер пока не нужно — сначала шаг 3.

### Шаг 3. Снять несовместимые ограничения

Готовый файл: [`docs/rollback/0008_drop_active_operation_limits.sql`](rollback/0008_drop_active_operation_limits.sql).

Он лежит **вне `drizzle/` намеренно**: всё, что попадает в `drizzle/`,
применяется автоматически на ближайшем деплое. Файл, положенный туда заранее
«на всякий случай», снял бы ограничения молча и в проде.

Копировать в `drizzle/` только сейчас, осознанно:

```bash
cp docs/rollback/0008_drop_active_operation_limits.sql drizzle/
docker compose -f docker-compose.prod.yml up -d --build
```

Раннер увидит новый файл и применит его при старте. Данные не меняются: снимаются
только два триггера и один индекс.

После отката файл остаётся в `drizzle/` как часть истории схемы — удалять его
нельзя, иначе базы, где он уже применён, и базы, где ещё нет, разойдутся.

### Шаг 4. Проверить

Открыть Operations, убедиться, что операции на месте и создание работает.

---

## 4. Когда без восстановления из копии не обойтись

Шаги выше не теряют данных, но лечат только ограничения. Восстановление из
резервной копии нужно, если повреждены сами данные — например, миграция
отработала не так, как ожидалось.

Порядок восстановления описан в README, раздел
«Резервное копирование и восстановление». Цена известна заранее: возврат к
моменту снятия копии, всё записанное позже теряется. Для системы, которая ведёт
остатки и себестоимость, это дорого — поэтому копия снимается непосредственно
перед деплоем, а не «когда-нибудь ночью».

---

## 5. Если миграция падает при накатывании

`0007` отказывается применяться к базе, где уже есть врач с двумя незакрытыми
операциями:

```
UNIQUE constraint failed: operations.doctor_id
```

Это не сбой, а защита: автоматически закрыть лишнюю операцию миграция не имеет
права — какая из них настоящая, знает только клиника. Найти нарушителей:

```sql
SELECT doctor_id, group_concat(case_code) FROM operations
 WHERE status = 'Active' AND doctor_id IS NOT NULL
 GROUP BY doctor_id HAVING COUNT(*) > 1;
```

Завершить или аннулировать лишние **через интерфейс** (Finish / Void), а не
прямым `UPDATE`: завершение пишет снимок итога, аннулирование возвращает
списанное на склад, и прямая правка статуса эти шаги пропустит, оставив остатки
неверными. После этого повторить деплой.

Контейнер при упавшей миграции не поднимается (`set -e` в entrypoint) — это
осознанно: приложение, пишущее деньги и остатки в схему, отличающуюся от
ожидаемой, хуже недоступного приложения.
